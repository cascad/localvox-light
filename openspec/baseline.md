# Принятие baseline — 2026-09-27

**`openspec/specs/` — источник правды о требуемом поведении LocalVox.**
Инвентаризация по коду завершена и преобразована в принятые контракты всех 15
capability. Основание: согласованные DEC-001–008, указания о пайплайне и именах
участников, затем поручение владельца: «доделай инвентаризацию, надо добить до
состояния спека — надежный источник правды». Повторного согласования этих решений
не требуется.

Это принятие требований. Оно не означает, что текущий код уже выполняет каждое
из них или установленная сборка прошла приёмку. Известный дефект больше не является
нормой только потому, что именно так работает код.

## Состав и границы

Исходный материал: `new_course`, HEAD `6dfde241bbeff1736829b0bf94c8d4c1f84b1517`
плюс незакоммиченное рабочее дерево. Перечитаны все требования и сценарии;
[журнал сверки](evidence/implementation-review-2026-09-27.md) содержит проверки
кода, файлов, mock-провайдеров и ограничения. [Матрица](evidence/coverage.md)
связывает каждое требование с реализацией, свидетельством и известным разрывом.
README/старые документы использовались как указатель тем, а не как доказательство.

Приняты неизменённые правила инвентаризации в явно указанном объёме. При обнаруженном
дефекте закреплено требование сохранять данные, честно подтверждать результат и
соблюдать уже обозначенные границы доступа.

| Решение | Нормативные требования |
|---|---|
| DEC-001: аудио до ручного удаления по умолчанию | STORE-003, PIPE-013 |
| DEC-002: независимая готовность результатов | PIPE-004/008/011, ARCH-001 |
| DEC-003: ограниченный ремонт, сохранение годной работы | PIPE-010/012, VER-004 |
| DEC-004: оригинал STT и отдельные исправления | VER-001, INV-VER-001, LLM-003 |
| DEC-005: сомнение отдельно от целостности | LLM-004/006, PIPE-007 |
| DEC-006: явный провайдер, без скрытого перехода в облако | LLM-005, ASK-001 |
| DEC-007: остановка до удаления, владение при изменении | PIPE-010/012, ARCH-005 |
| DEC-008: локальная заметка до доставки | NOTE-006, VOICE-004 |
| Не узнавать людей между разговорами | SPK-002/003 |
| Артефакты, честные время/активность, ограниченный параллелизм | PIPE-003–011 |
| Управление без PCM и диагностируемая остановка | INV-REC-002, INV-RUN-001; PIPE-010 |

Для выявленных расхождений норма также уточнена: обе ошибки поиска не равны
«ничего нет» (SEARCH-002/CHAT-001), snapshot не равен Live (CFG-002), отсутствие
классификации не разрешает выдачу секретов (CFG-003), media сохраняет общую границу
доступа (API-002), FLAC проверяется до удаления WAV (STORE-002), коллизия имени
не разрешает перезапись заметки (NOTE-002), ошибка confirm не равна успеху (LLM-006).
Конкретные дефекты и воспроизведения сохранены в [review](review.md).

Численного обещания скорости нет: benchmark BL-003 ещё нужен. Windows — платформа
выполненных проверок; аппаратная запись, LAN/mobile, другие ОС и реальное качество
моделей требуют отдельных прогонов. Ограничения вроде сегментных таймкодов, возможного
дубля внешней доставки или отсутствия гарантии при потере питания описаны явно.
Пожелания из BL-011–017 не стали реализованными или обязательными функциями.

Базовое редактирование сохраняет исходный STT, структуру реплик и смысл. Более
сильная переформулировка/сокращение, новый default провайдера, численный бюджет
скорости и новые платформы — будущие продуктовые изменения с примерами и проверками.
Они не разрешены молчаливой интерпретацией текущего контракта.

## Что теперь считается изменением

1. Баг: код нарушает существующее требование. Исправляем код по сценарию; не ослабляем
   требование, чтобы сделать тест зелёным. В change ссылаемся на ID и фактический отказ.
2. Новое поведение: proposal → delta specs → design/tasks → реализация/проверки →
   sync/archive. Сырая идея может остаться только proposal до груминга.
3. Новое свидетельство: обновляем матрицу и evidence с командой, результатом и
   пределами. Наличие теста не равно его выполнению, один прогон не покрывает все сценарии.
4. Исправление неточного текста без смены смысла: правим spec и связь с кодом;
   если меняется обязанность приложения, это уже поведенческое изменение.

Однократное принятие baseline включает известные ещё не реализованные обязательства
из таблицы выше. Это не sync невыполненных changes и не их закрытие. В дальнейшем
нельзя переносить предложение в действующий контракт без принятого решения или
объявлять его реализованным. Незавершённые changes должны уточнять/реализовывать
эти требования, а не повторно спрашивать уже принятое направление.

## Проверка актуальности

Из корня репозитория:

```powershell
$env:OPENSPEC_TELEMETRY='0'
openspec validate --specs --strict --no-interactive
python scripts/check-openspec.py
```

Первая команда проверяет штатный формат OpenSpec. Вторая — уникальные ID,
полное покрытие матрицей, WHEN/THEN, привязки к исходникам и локальные ссылки/якоря.
Ни одна не доказывает семантическое соответствие кода; для изменённых требований
нужны описанные в них сценарии, подходящие тесты и обновлённое свидетельство.

Работающий release-демон и пользовательский архив при этой работе не изменялись.
Открытые BL/RV не закрыты принятием baseline.
