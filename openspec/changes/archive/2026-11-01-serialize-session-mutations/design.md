# Проект решения

## Context

Координатор, обычный CLI и recook уже используют .worker.lock, но delete/best/имена и порядок set_lang имеют другие границы.

## Goals / Non-Goals

Цель: согласовать владение изменяемой сессией. Не включать глобальную перестройку хранилища и бессрочное
расширение гарантий на все процессы приложения.

## Decisions

### Уточнение по исходникам, 2026-11-01

- Сейчас delete вызывает forget_session до remove_dir_all и игнорирует save error;
  request-stop на отдельную сессию отсутствует. Global shutdown AtomicBool нельзя
  использовать для cancel одной записи: он останавливает весь координатор.
- Добавить durable состояния Cancelling/Cancelled с сохранением phase и прежних
  clocks/artifacts. Cancelling запрещает новый claim/advance/retry; Cancelled —
  терминальный исход с фактическим finished_at, не Failed/Done. Обычный read,
  discovery, recovery и automatic revival не возобновляют отменённую работу.
  Явный ручной retry может продолжить ту же фазу с проверкой сохранённого результата.
- В процессе daemon общий core registry связывает canonical session path,
  job/execution и отдельный atomic stop token с живым execution lease. Register
  выполняется внутри claim mutex; guard удерживает lease до завершения supervisor
  и сохранения исхода, unregister происходит после освобождения lease. API не
  посылает сигнал произвольному PID/стороннему CLI.
- Все API-мутации сначала неблокирующе получают отдельный session control lease,
  затем execution lease. Обычные recook/best/lang/names сразу отказывают при
  конфликте. Cancel/delete могут ждать освобождения только управляемого владельца;
  под jobs mutex нет ожидания OS lock или завершения процесса.
  Используется точный ID каталога из списка архива; канонический parent и имя
  проверяются до первого изменения, чтобы другой регистр/alias не создал второй
  tombstone для той же записи и не оставил настоящее задание исполняемым.
- Cancel/delete проверяют recording/confirm/path до изменения намерения. Под jobs
  mutex проверяются owner/lease и сохраняется Cancelling; только успешный commit
  разрешает stop token. При свободном execution lease сохраняется Cancelled сразу.
  Подтверждение API требует реально полученного execution lease и сохранённого
  Cancelled; heartbeat, отсутствие registry entry и timeout не заменяют владение.
- Supervisor проверяет token вместе с global running. Даже при гонке exit=0 с
  cancel finish/failure не могут затереть Cancelling: их commit возвращает особый
  non-failure исход. Владелец сохраняет Cancelled после остановки дерева, удерживая
  lease. При storage error повторяет только commit; restart завершает отмену при
  подтверждённо свободном lease, а не возвращает её в Pending.
- Delete после подтверждённой остановки удерживает оба lease, удаляет каталог и
  лишь затем очищает queue tombstone. При отказе остановки/commit каталог не
  трогается; при неудачном удалении Cancelled не даёт discovery воскресить работу.
  Позднее освобождение после истечения серверного ожидания остановки не вызывает отложенное удаление.
- Cancel/delete не останавливают активную запись аудио и не обещают отменить
  вычисление внешнего Ollama. Процессное дерево принадлежит supervisor (BL-018),
  внешний LLM — отдельная служба. Несколько файлов не становятся транзакцией от
  одного lock: queue fence сохраняется до файловых операций, последствия ошибок
  после физического удаления описываются отдельно от отказа остановки.
- UI/TUI показывают остановку и отмену отдельно от ошибки/Done; подтверждённый
  текст доступен, незавершённое не выдаётся за готовое. Команда отмены и явный retry
  используют общий backend, справочник US-ID обновляется вместе с поведением.

Выделить общий guard на сессию и определить порядок lock с jobs mutex. Не превращать отсутствие heartbeat в разрешение обойти живую блокировку. Отдельно решить частичный commit нескольких файлов; lock сам не делает транзакцию.

По [DEC-007](../../review-code-inventory/proposal.md#dec-007) отмена/удаление проходят
через управляющую остановку владельца и подтверждение освобождения сессии; удаление
затем само получает guard. Между остановкой и удалением координатор не должен
повторно захватить эту запись. Отменённое задание не должно автоматически оживать
из-за обычного retry/recovery. Существующие артефакты сохраняются при отмене и
неуспешном удалении. Для стороннего CLI без доступного управления нужен объяснимый
отказ, а не обход lock. Точный протокол требуется перепроверить с BL-018.

Для остальных мутаций оставлен уже предложенный явный конфликт до записи:
это не добавляет очередь отложенных пользовательских действий. Альтернатива с
отложенным выполнением требует правил отмены и устаревания намерения и в этот
scope не входит. Прежний безусловный отказ delete заменён управляемой остановкой.

## Risks / Trade-offs

Не принимать описание механизма за доказательство crash-safety. Работа затрагивает
повтор/отказ и должна иметь проверку на временном архиве; нужен ревью выбранного поведения.

## Verification

Промежуточная реализация 2026-09-27: API удерживает session lease до первой записи
и до окончания invalidation/queue. Порядок API: execution lease → jobs mutex;
координатор: jobs mutex → НЕБЛОКИРУЮЩИЙ try_execution_lock. Ожидания lock под
mutex нет. set_lang восстанавливает прежнюю meta при отказе recook. Проверен
отказ всех шести мутаций при живом владельце с побайтовой проверкой артефактов.
Delete пока только отказывает при занятости: cancellation/tombstone ещё не
реализованы. Lock не делает несколько файлов транзакцией; задачи 1.1–1.4 открыты.

Проверить конкурирующие операции на временной сессии с удерживаемым lock, успешную
и неудачную остановку перед delete, сохранение результатов при cancel, отсутствие
повторного захвата/автоматического возобновления и отказ записи между изменениями.

Итог 2026-11-01: реализованы общий control/execution lease, durable отмена,
подтверждение реальной остановки, безопасный порядок удаления и ручное продолжение.
[Выполненные проверки и оставшиеся границы](evidence/implementation.md) дополняют,
а не переписывают промежуточные результаты выше. Частичное физическое удаление
не откатывается: при файловом отказе сохраняется cancellation fence; полная
многофайловая транзакция и power-loss durability не заявлены.
