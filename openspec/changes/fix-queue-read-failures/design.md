# Design

## Context

См. proposal/Why. JobQueue::load намеренно сохраняет load_error и пустую внутреннюю структуру; мутации запрещены, progress возвращает queue_error. Два остальных читателя API берут jobs без проверки error. Клиентские polling уже сохраняют прошлый успешный snapshot и очищают ошибку после успешного чтения.

## Goals / Non-Goals

Согласовать отображение queue/jobs с существующими PIPE-002/011. Не чинить и не перезаписывать повреждённый файл, не трогать retry/claim/discovery и BL-002/004, не добавлять автоматические повторы изменяющих запросов.

## Decisions

- Archive queue/jobs возвращают Result через единый проверенный загрузчик. Нечитаемое хранилище помечается типизированной ошибкой QueueUnavailable; HTTP переводит именно её в 503. Это лучше поиска слов в сообщении: имя файла или текст I/O не должны менять код ответа. Успешные JSON неизменны; отсутствующий jobs.json остаётся штатной пустой очередью.
- UI получает error jobs polling и показывает постоянный индикатор недоступности с пояснением и, если есть snapshot, последними счётчиками. Строка ошибки открывает ту же очередь, начальная ошибка не создаёт нулевые счётчики. Текст ответа идёт через обычный escaped React text/title.
- TUI сохраняет данные через существующий App::apply и показывает ошибку в списке/статусе; верхняя строка при jobs error сообщает недоступность вместо неподтверждённых чисел. Нового хранилища snapshot и нового wire-поля не требуется.
- Ошибка фонового чтения хранится только у ресурса, без копии в постоянном status. Иначе после успешного ответа там остаётся прежнее «Ошибка». Постоянный результат Action/Control/Route сохраняется; успешный фоновой GET его не стирает.
- Повторное чтение использует существующий backoff клиентов. Отдельный запасной список или успешный JSON с нулями скрыли бы сбой и нарушили контракт.

## Risks / Trade-offs

- Смена Rust API signatures затронет потребителей → проверить все call sites компилятором и настоящим HTTP/client тестом.
- HTTP-клиент может скрывать внутреннюю причину для удалённого клиента → проверить прежнее редактирование ошибок отдельно, не раскрывать дополнительные сведения ради диагностики.
- 503 не запускает ремонт файла → ошибка остаётся видимой до восстановления доступности; tests меняют только временное хранилище.

## Migration Plan

Миграции файлов нет. Собрать UI и API обычным способом, затем обновить установленную сборку отдельно. Откат — возврат исходников/пересборка; пользовательские данные не меняются.

## Validation

Real HTTP: missing/empty, malformed JSON и ошибка чтения (каталог вместо jobs.json), 503 обоих endpoint, неизменность байтов/каталога, восстановление правильного файла с running/pending/failed. UI: начальная ошибка queue/jobs, устаревшие счётчики/строки и восстановление. TUI: retained snapshot, отметка в header/list, очистка ошибки после успеха, символы/цвет. Затем полный API/UI/TUI и общий временный API-сценарий; TEMP/TMP тестов на D:.
