# Сверка и принятие инвентаризации

## Context

См. [proposal](proposal.md) и [baseline](../../baseline.md). Владелец сначала
согласовал DEC-001–008, затем поручил завершить инвентаризацию в надёжный источник
правды. Все 15 capability прочитаны; рабочее дерево dirty, у пользователя работают
release-демон и окно. Известные дефекты нельзя переносить в контракт как норму.

## Goals / Non-Goals

Завершить аудит и принять полный baseline с проверяемой связью требования и кода.
В этот документационный change не входит реализация всех обнаруженных дефектов,
приёмка реальных устройств/качества моделей или обновление пользовательского архива.
Поведенческие исправления остаются в отдельных native changes.

## Decisions

- Разделить три оси: принятие контракта, соответствие реализации, уровень свидетельств.
  Все требования получают accepted; известные gaps остаются открытыми у своих ID.
  Простая замена заголовка старого снимка была отвергнута: она узаконила бы баги.
- Сохранить официальный формат Requirement/Scenario без собственного DSL.
  В каждом требовании — вход/поведение/отказ/код; единая Markdown-матрица обеспечивает
  полное покрытие ID. Чекер проверяет структуру, но не объявляет семантику доказанной.
- Выполнить изолированный mock отказа/повтора доставки. Не использовать действующие
  slots, внешние сервисы, реальные заметки или перезапуск пользовательского демона.
- Принятые DEC встроить в main specs при однократном принятии baseline; дальнейшее
  изменение смысла — через delta. Незавершённые changes при этом не закрываются.
- Не обещать неподтверждённую скорость, качество, устройства или более агрессивное
  редактирование. Их расширение требует отдельного намерения и сценариев.

## Risks / Trade-offs

- Accepted можно спутать с implemented → явные Implementation status и GAP в матрице.
- Тест существует, но не выполнялся → test-linked отделён от test-run с датой/командой.
- Старый release может отличаться от source → журнал называет рабочее дерево и границы.
- Ссылки/ID могут устареть → check-openspec проверяет полноту и локальные цели.
- Неизвестный исход доставки → mock фиксирует возможный дубль, exactly-once не обещается.

## Migration Plan

Перечитать все требования, завершить mock, убрать дефекты из нормативных формулировок,
записать матрицу и baseline, обновить AGENTS/config/навигацию, проверить штатный
валидатор и ссылки. Миграции данных и рестарта приложения нет. Исторические отчёты
сохраняют прежние результаты; новая запись фиксирует переход.
