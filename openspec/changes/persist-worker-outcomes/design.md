# Design

## Context

См. proposal/Why. Finish_phase уже откатывает Job при save failure, но координатор не отличает этот отказ от невалидного артефакта. Mark_failed игнорирует save; fail_phase сначала пишет progress. Линия держит execution lock вокруг run_phase, поэтому ожидание внутри принятия результата сохраняет владение без нового запуска.

## Goals / Non-Goals

Подтвердить результат/отказ после записи; не переводить валидный результат в worker failure при временном отказе хранилища. Не менять mark_done/clear_force/удаление, политику попыток, форматы или вводить общую транзакцию queue/progress. Не перезапускать пользовательский демон для проверки.

## Decisions

- Тип QueueStorageError внутри anyhow отделяет load/save failure от неверного задания/артефакта. Существующий Result API finish сохраняется; общий commit_jobs сохраняет rollback. Checked try_mark_failed возвращает ошибку, совместимый mark_failed сохраняет прежнюю сигнатуру и откат.
- Координатор повторяет только storage errors до успеха или stop flag, освобождая mutex на каждой попытке и паузе. Это сохраняет execution lock и не запускает worker повторно. Остальные ошибки остаются ошибками обработки.
- При первом ожидании создаётся одна операция журнала с явным названием «Ожидание сохранения очереди» и execution binding. Она закрывается при принятии/остановке. Ошибки журнала не блокируют первичную очередь; бесконечный набор строк на каждой паузе не создаётся. Это диагностика ожидания, не новый глобальный монитор всех I/O.
- Failed stage event пишется после успешного try_mark_failed. Stop оставляет Running для штатного restart recovery. Между записью очереди и диагностикой остаётся crash window, не exactly-once.
- Новый docs/user-guide.md кратко описывает пользовательские входы с US-ID; исторический user-scenarios.md и S-ID остаются. Правило AGENTS.md требует обновлять справочник вместе с изменением поведения.

## Risks / Trade-offs

- Долгая блокировка файла удерживает ресурсную линию → пауза с stop flag, видимая операция; блокировка очереди между попытками освобождается. Другие линии и API не держат этот mutex за нас.
- Невалидный артефакт при работающем файле → не ждать бесконечно, сохранить обычный отказ по прежним правилам.
- Недоступность и чтения, и записи → типизировать оба случая; не заменять повреждённый файл пустым.
- Неподдерживаемые действия в справочнике → сверить все действия UI и палитры TUI, отдельно отметить настройки/CLI и известные границы.

## Migration Plan

Миграция данных и новые зависимости не нужны. Проверки на temp-очередях, модели не запускаются. Обычное обновление бинарника отдельно от аудита; откат через исходники/пересборку.
