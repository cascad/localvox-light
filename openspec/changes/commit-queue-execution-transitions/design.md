# Design

## Context

См. proposal/Why. Finish_phase и ручной retry уже откатывают свой Job при save failure. Start/reclaim/revive этого не делают; два последних игнорируют save и возвращают положительный count. Reclaim пишет progress перед сохранением очереди. Startup вызывает его один раз и запускает линии даже при отказе.

## Goals / Non-Goals

Подтверждать три перехода после сохранения и не тратить бюджет/идентичность на отказах. Не менять успешную очередь, retry policy, API payload и оформление UI/TUI. Другие mutators JobQueue, полный аудит I/O и crash-транзакция queue/progress не входят в этот срез; BL-002/004 остаются открытыми.

## Decisions

- Checked try_start/try_start_phase, try_reclaim_abandoned и try_revive_failed возвращают Result. Совместимые методы start/start_phase/reclaim_abandoned/revive_failed сохраняют прежние типы, но на ошибке возвращают None/0; существующие ошибки save логируются. Это не требует массовой замены пользователей старого API.
- Сохранять предыдущие Job только затрагиваемых индексов. При отказе вернуть snapshot; при отсутствии кандидатов не записывать файл. QueueFile.next_id эти операции не меняют. Checked методы отдельно отказывают при load_error.
- Reclaim закрывает interrupted progress после принятого сохранения. История и готовые артефакты сохраняются; ошибка progress не откатывает уже принятую очередь. Общая атомарность двух файлов не обещается.
- Startup helper повторяет checked recovery с кооперативной паузой, публикует blocked/причину до восстановления, ready только после успеха. Линии создаются после этого барьера. Maintenance использует checked revival, не пишет ложный success count; при ошибке даёт диагностику и повторяет на следующем цикле.
- Claim остаётся совместимым Option: None не допускает запуск worker, следующий цикл повторяет Pending после восстановления записи. Этот срез не вводит отдельный глобальный монитор записи для всех операций/процессов.

## Risks / Trade-offs

- Несколько Job в batch → rollback всей изменённой группы при одном неудачном save; тест с несколькими кандидатами.
- Непишущийся файл во время startup → bounded кооперативные паузы и stop flag; тест реального Windows deny-replace и восстановления.
- Ошибка чтения не равна отсутствию работы → checked API отказывает до изменений, битый jobs.json не перезаписывается.

## Migration Plan

Формат данных и старые method signatures совместимы. Обновить бинарник обычной сборкой отдельно от аудита; пользовательский демон не перезапускать. Откат — исходники/пересборка, миграция архива не нужна.

## Validation

До исправления три core fault tests воспроизводят изменённую память/ложные counts/history. После: отказ и повтор на том же объекте, несколько jobs, read error, сохранение фаз/бюджета/истории; настоящий startup recovery после release файлового запрета и штатная остановка без worker. Затем jobs/workflow/progress, autocook/API tests по риску, UI и общий temp API/UI/TUI последовательно, строгие main/change/check-openspec/format/diff. TEMP/TMP процессов на D:.
