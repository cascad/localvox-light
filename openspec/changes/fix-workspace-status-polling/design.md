# Design

## Context

См. [proposal](proposal.md) и [API-006](specs/api-access/spec.md).
App объединяет sessions/record/jobs через Promise.all каждые 5 секунд и отдельно
читает record каждую секунду. usePolling уже используется журналом/очередью и
делает последовательные GET с backoff, но не предоставляет явного refresh.
RecordBar отдельно подтверждает start/stop; эти GET должны оставаться независимыми
от медленного фонового чтения и не менять правила подтверждения REC-001/003.

## Goals / Non-Goals

Сохранить ритмы 5 секунд для архива/заданий и 1 секунду для записи, последнюю
успешную информацию и существующий вид ошибок. Не менять сервер, start/stop,
таймаут подтверждения, пользовательские данные, плеер и чтение артефактов.

## Decisions

- Три usePolling вместо общего reload с Promise.all. Ответ ресурса публикуется
  сразу; соседний запрос не является его барьером. Это устраняет второй фоновый
  источник record в медленном цикле.
- Стабильный refresh в usePolling очищает timer, отменяет активный GET и создаёт
  новое поколение. До начала нового GET проверяется актуальность поколения;
  поздние resolve/reject старого поколения отбрасываются даже без поддержки abort.
- Периодический повтор планируется только после завершения текущего чтения.
  Сохраняются существующие ограниченный backoff, ключ ресурса и cleanup при unmount.
- После пользовательского действия общий refresh обновляет три ресурса. Он не
  повторяет mutation и не ждёт старый снимок. Выбор текущей записи сохраняется;
  начальный выбор происходит после первого доступного списка сессий.

## Risks / Trade-offs

- Подтверждённый start/stop затирается старым GET → удерживаемый record, настоящий
  клик start и поздний release; отдельная проверка abort активного чтения.
- Принятая запись исчезает после старого списка → импорт при pending sessions,
  новый список и поздний release, сохранение выбора/вкладки.
- Изменение общего hook затрагивает progress/queue → полный browser e2e и прежние
  screenshots, отдельная ошибка/восстановление и настоящий общий API/UI/TUI-сценарий.
- Abort прекращает ожидание клиента, а не гарантирует прекращение работы сервера.
