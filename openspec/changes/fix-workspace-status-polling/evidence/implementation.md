# Опрос состояния рабочего пространства · 2026-11-01

Продолжение проверки задержек и рефакторинга UI по поручению владельца.
Пользовательский архив, .env, работающий демон и устройства не изменялись.

## Исходный отказ

App каждые пять секунд ожидал sessions/record/jobs через общий Promise.all,
одновременно отдельный setInterval читал record каждую секунду. Эти циклы не
проверяли, закончился ли предыдущий GET. Публикация списка/счётчиков ждала
соседние ресурсы; старое чтение могло завершиться после явного обновления.

Три теста `workspace ... polling never overlaps a slow background GET` выполнены
до исправления. При удерживаемом ответе и двух продвижениях виртуальных часов
по 5100 ms получены FAIL: sessions 2, jobs 2, record 3 при expected 1.
Локальный лог: target/status-polling-before.log. Это mock HTTP и подсчёт запросов,
не замер скорости моделей или производительности пользовательского архива.

## Реализация и проверки API-006

- [App](../../../../ui/src/App.tsx): три независимых последовательных poll;
  архив/задания — 5 секунд после ответа, запись — 1 секунда. Второе фоновое
  чтение record из общего reload убрано. Начальный выбор записи идёт после
  получения списка, последующие обновления выбор сохраняют.
- [usePolling](../../../../ui/src/usePolling.ts): стабильный refresh, отмена
  активного GET, поколение чтения, защита поздних resolve/reject, очистка timer
  и controller. Начало отложено до microtask с проверкой живого поколения;
  пробный lifecycle React не выполняет оставшееся чтение закрытого контекста.
  При ошибке сохраняются данные и прежний backoff до 30 секунд; явный refresh
  сбрасывает backoff. Snapshot помечен key и не выходит в другой контекст.
- [api.ts](../../../../ui/src/api.ts): только необязательный AbortSignal в
  sessions/jobs/record, без изменения URL, payload, авторизации и таймаутов.

В [браузерных тестах](../../../../ui/tests/e2e/workspace.spec.ts) выполнены:

1. Нет перекрытия удерживаемых sessions/jobs/record.
2. При медленном архиве публикуются новые jobs и recording; при медленных jobs
   либо record публикуется свежий архив — проверены оба направления зависимости.
3. После подтверждённого start и stop старый фоновый GET отменяется; его поздний
   release не меняет новый статус. Start/stop отправлены ровно по одному разу.
4. Импорт при pending sessions отменяет старый GET; новая запись остаётся выбранной
   на «Ход», поздний старый список её не убирает, POST ingest ровно один.
5. При 503 архив и открытый документ сохраняются; после backoff отображается новый
   список и ошибка снимается. Проверяется, что повтор не наступил раньше задержки.

Отмена наблюдается на signal реально вызванного fetch только до его завершения,
а не на уже успешном запросе. В start-сценарии тест ждёт именно отмену старого GET
и фактический индикатор recording: кнопка «Остановить» доступна ещё до подтверждения.
Первый вариант теста ожидал только эту кнопку и преждевременно освобождал ответ;
исправлена синхронизация проверки, поведение RecordBar не менялось. Другие начальные
отказы тестов были слишком точными локаторами заголовка: реальная подпись содержит
«· добавлено 10:00». Локаторы учитывают существующую подпись; вёрстка не менялась.

Первый настоящий совместный прогон выявил гонку в
[actual-api.mjs](../../../../ui/tests/integration/actual-api.mjs): после сохранения
summary=off тест ждал только локальное значение select, затем немедленно читал .env.
Файл содержал предыдущее сохранение модели; в trace POST настроек ещё ожидал ответа
(status -1), в отличие от предыдущего успешного POST со status 200. Теперь тест
ждёт успешный ответ POST /api/settings и состояние «Сохранено», затем проверяет
файл. Это исправление проверки, без изменения Settings/API и без увеличения timeout.

Следующий совместный прогон не дождался terminal-reconnected. Автоматическая
навигация [ConPTY fixture](../../../../crates/localvox-light-api/src/http/tests/cross_clients.rs)
теперь отдельно ждёт форму подключения перед Ctrl+S и исчезновение формы перед
переходом из списка в документ. При общем deadline сохраняются финальный экран,
ANSI и флаги стадий, вместо потери диагностики. Промежуточная проверка ошибочно
требовала заголовок «Архив» на компактном экране списка; реальный экран показывает
«Список · Enter открыть». Проверка исправлена по захваченному экрану. Таймауты
45/60 секунд и все итоговые требования совместного сценария сохранены; продуктовый
TUI при этих уточнениях не менялся.

Timeline отдельного прогона показал 17.6 секунды между отправкой клавиш и появлением
формы подключения: fixture шёл вниз через 31 пункт палитры. Прогон прошёл за 45.33 s,
близко к общему deadline. Теперь позиция берётся из типизированного COMMANDS/Action,
выбирается короткое направление навигации (для текущего каталога семь шагов вверх).
Форма, reconnect, чтение того же документа и все прежние итоговые проверки сохранены.
В финальном прогоне marker был записан до того, как браузер начал его ждать.
Terminal/browser timeline сохраняются в test-results и входят в обычные CI artifacts.

## Границы

REC-001/003: проверены клиентские команды и подтверждения через mock HTTP, не
физический захват. Сам RecordBar/его таймаут подтверждения не изменялись; управляющие
GET остаются отдельными от фонового poll, чтобы не ждать занятую полосу.

новые индикаторы недоступности в этом срезе не вводились.

Общий usePolling также обслуживает Progress/Queue; их существующие browser-сценарии
входят в полный прогон. Чтение артефактов управляется отдельным useArtifact и не
менялось. Snapshot baseline не обновлялись. Rust-код TUI не менялся, его прежние
95 тестов не выдаются за новый отдельный прогон. Аппаратная приёмка 10.2 общего
журнала, настоящие модели, двухчасовая запись и BL-003 остаются not-run.

API-006 хранится в delta, main specs не синхронизированы, changes не архивировались.
