# Design

## Context

Мотивация и границы — в [proposal](proposal.md), поведение — в [delta specs](specs/technical-journal/spec.md) и [terminal-workspace](specs/terminal-workspace/spec.md). Реализация идёт по этому плану; фактические проверки — в [evidence](evidence/implementation.md), незавершённые работы — в [tasks](tasks.md).

Проверено чтением текущего кода:

- Rust workspace содержит демон/координатор, worker, HTTP API, ASR/LLM, поиск, интеграции, voice и старый TUI. `ui/` — React/TypeScript/Vite, `src-tauri/` открывает тот же API/frontend.
- `localvox-light/src/main.rs` в старом TUI-режиме создаёт engine, передаёт ему канал `UiMsg` и при выходе завершает его. В daemon-режиме API/запись принадлежат демону. Эти модели жизненного цикла нельзя смешивать.
- Старый `localvox-light-tui` — экран live-текста, уровней, логов и устройств, а не архивное приложение. По указанию владельца его код не переносится; можно смотреть на него для справки.
- React уже имеет пять разделов и пять вкладок документа, плеер, запись и около тридцати групп действий. Точный перечень — [parity.md](parity.md).
- `progress.jsonl` хранит события этапов и границы запусков. `activity()` сообщает heartbeat и пишет границы операции в tracing, но HTTP `/progress` отдаёт свёрнутые состояния. Поэтому рисовать вложенную историю по одному `/progress` недостоверно.
- `localvox-light-process` уже ограничивает spool stdout/stderr, время и дерево процессов. Результат stdout/stderr сейчас передаётся вызывающему коду после завершения. Не заменять его pipe-reader потоками ради косметики.
- В `ui/package.json` нет тестового runner, а текущий CI собирает UI/бинарники; наличие Rust-тестов не означает проверку графики или нового клиента.
- [Исторический разбор](../../../docs/processing-pipeline.md) содержит 16 минут 20 секунд ожидания перед стартом одного видео и около 8 минут 22 секунд после старта. Это старый случай, а не текущий benchmark или доказанная причина нынешней медлительности.

## Goals / Non-Goals

**Goals:**

- Два клиента одного приложения, одинаковые действия/результаты при подходящих для среды вводе и компоновке.
- Новый самостоятельный TUI, который можно разрабатывать и тестировать без микрофона и загрузки моделей.
- Журнал с реальными границами, состояниями и деталями, удобный при длительной работе и ошибках.
- Тесты действий и визуала входят в каждый этап реализации, а не откладываются до финальной чистки.

**Non-Goals:**

- Обещать ускорение ASR/LLM, изменять scheduler/модели, внедрять постоянный STT-worker либо делать массовый рефакторинг. Это отдельные BL-003/008 и последующие изменения по измерениям.
- Переносить старые TUI-буферы, capture-controls, локальные мутации файлов или структуру его экранов в новый клиент.
- Считать raw stdout подтверждением результата, рисовать несуществующие операции, добавлять паритет с нереализованными идеями из старых документов.

## Decisions

### 1. Два клиента, один сервер

```text
React / Tauri --------------------+
                                  +--> HTTP API --> daemon / queue / workers
localvox-tui --> HTTP client ------+
       |
       +--> owned audio player --> HTTP media
```

Создать новый crate `localvox-light-terminal`, binary `localvox-tui`. Новый crate `localvox-light-client` содержит только wire DTO, кодирование URL, авторизацию, таймауты и HTTP-вызовы. Он не зависит от `localvox-light-core`, capture, Vosk/ONNX, API-server или React build. Сервер не зависит от клиентского crate.

Использовать имеющиеся Ratatui/Crossterm и `ureq` workspace: синхронный HTTP из ограниченного набора I/O-потоков. Добавлять общий async-runtime ради интерфейса не требуется. Интерфейсы вводятся на HTTP, playback, clipboard и lifecycle; domain-состояние/компоновка остаются конкретными типами. Wire-формат проверяется общими синтетическими JSON fixtures в Rust и TypeScript; собственный генератор API не нужен.

Альтернативы: прямой доступ TUI к `Archive` привязал бы клиент к локальному диску и тяжёлым зависимостям; встраивание нового TUI в capture-процесс повторило бы связь закрытия окна с записью. Использовать API — уже работающая граница React/Tauri.

### 2. State / update / render отдельно от I/O

`app` содержит состояние навигации, выбор сессии, вкладку, черновики, раскрытие блоков, позицию чтения и модальное действие. Чистая функция обновления принимает событие и выдаёт новое состояние/эффекты; render получает только снимок и размер экрана. Clock, ID запросов, адрес/токен и внешние зависимости создаются при запуске и передаются событиями.

Ответы I/O несут generation выбранного контекста и request ID. Поздний ответ A не применяется к B; повторы same-segment seek получают отдельный nonce. Изменяющие запросы не повторяются автоматически при timeout/lost-ack. Пользователь видит неопределённый исход и может перечитать серверное состояние.

Планируемые ограничения: до четырёх одновременных HTTP-запросов на клиент, ограниченная очередь эффектов, один in-flight poll каждого ресурса, один экземпляр playback. События перерисовки/heartbeat коалесцируются. Это пределы клиента, не обещание пропускной способности сервера.

### 3. Терминальное рабочее пространство

```text
+------------------------------------------------------------------+
| localvox   record: idle     queue: 2     connection: live          |
| player: paused   02:14 / 30:28                                    |
+--------------------+------------------------------+--------------+
| Archive            | Summary | Lines | Text | ... | Context      |
| Notes              |                              | Versions     |
| Queue              | document or operation tree   | Sources      |
| Ask                |                              | Actions      |
| Settings           |                              |              |
| sessions / history |                              |              |
+--------------------+------------------------------+--------------+
| Tab focus   / search   : actions   ? help   Ctrl+Q close client   |
+------------------------------------------------------------------+
```

Это новый клиент с поведением окон, а не отдельная лента логов. Документы занимают основную панель, журнал — вкладку «Ход»/очередь и компактную область текущей активности. Плеер и состояние записи находятся в постоянных строках. Правая панель содержит контекст текущего документа, а не дублирует запись.

Первоначальная карта клавиш: `Tab`/`Shift+Tab` между панелями; стрелки/`j,k` в списках вне редактора; Enter открыть/раскрыть; Left/Right свернуть/раскрыть дерево вне текстового ввода; `/` поиск; `:` палитра; `?` помощь; `Ctrl+Q` закрыть клиент. Start/stop доступны через видимую кнопку/палитру и документированное сочетание, которое не конфликтует с вводом. Точное сочетание проверяется в Windows Terminal до фиксации snapshot; печатная буква в редакторе не запускает действие.

Широкий терминал — три панели; средний — список и документ с переключаемым контекстом; 80×24 — одна активная панель с сохранением записи/ошибки/подсказок. При размере ниже пригодного минимума показывается компактный экран с доступным stop и выходом. Переключение размеров сохраняет выбор, формы и scroll.

Многострочный ввод — отдельный редактор с bracketed paste. Подтверждения именуют конкретный объект и действие. Clipboard реализуется через небольшой OS adapter; при недоступности — объяснимая ошибка и сохранение текста в выбранный пользователем файл, а не ложное «скопировано». OSC 52 по умолчанию не отправляется.

### 4. Общая эстетика, два рендерера

Роли: background/surface/text/dim/line, command/argument/value/path, active/success/warning/error, selection/focus. Стартовая тёмная палитра: фон `#17191d`, основной текст `#d8dce3`, вторичный `#9ca4af`, разделитель `#343942`, команды `#85b4dc`, аргументы `#c2a5d8`, значения `#d6c28b`, успех `#7fbd9a`, активность `#d8b777`, ошибка `#e38d85`. Это предложенные токены, проверяемые на читаемость; существующие light/dark/system настройки UI сохраняются.

Основной ритм — строки, отступы, тонкие разделители и ветки `└`/`├`/`│`; ASCII fallback — `+`, `-`, `|`. Малые символы + подпись кодируют статус даже без цвета. Нет повсеместных крупных карточек, вложенных рамок и мигания завершённой работы. Моноширинная типографика — для интерфейса/журнала; документы сохраняют удобную длину строк и иерархию заголовков.

В UI добавить Journal-компоненты и токены поверх имеющихся действий; не переписывать одновременно все сетевые flows. В TUI написать renderer заново. Общими являются семантика и fixtures, а не runtime HTML/CSS внутри терминала. Пользовательское действие в палитре — действие API; настоящая команда worker отображается только по безопасному событию producer.

### 5. События и API живого журнала

Расширить существующий append-only `progress.jsonl` обратно совместимыми записями операций. Старые `StageEvent` и run-маркеры остаются читаемыми, `/progress` сохраняет формат. Новые записи несут версию схемы, run ID, operation/parent ID, время, kind и безопасные display-поля; серверный cursor идентифицирует порядок записей независимо от одинаковых timestamp.

Producer событий — существующие границы prepare/STT/refine/cleanup/summary, `activity`, запуск/завершение supervised-команд. Чётко различать «операция закончила выполняться» и «фаза/артефакт подтверждены». В том числе `activity<T>` не позволяет объявить generic T успешным результатом без принятия артефакта. Запись подробностей ограничена; сбой диагностики не меняет подтверждение результата.

Добавить `GET /api/sessions/{name}/journal` с `after` либо `before`, `limit`, ответом `events`, `next_cursor`, `has_more`, `reset`, `truncated` и диагностикой нечитаемых записей. Обычные API-правила авторизации. Плановые пределы: 200 событий / 256 KiB ответа, 1 MiB сканирования на запрос, 4 KiB display-текста одной записи. Возврат обрезки/продолжения явный; giant/malformed строка не должна зациклить cursor.

Начальная загрузка читает ограниченный хвост, продолжение — с курсора; никаких полных read-to-string на каждый poll. Каждая новая запись несёт run ID, чтобы хвост не требовал поиска начала длинного запуска. Legacy-события без ID показываются как известные этапы без выдуманной вложенной детализации. Если файл заменён/обрезан, клиент получает reset и перечитывает актуальный хвост. Run-boundary не стирает историю, текущий запуск выделяется явно.

Низкоуровневые stdout/stderr не публикуются целиком автоматически. Структурированные информационные сообщения дают live-детали. Для разрешённого вывода внешнего процесса добавить ограниченный incremental-read callback к уже имеющемуся spool-supervisor: частичные строки, лимит вывода, неблокирующий sink и управляемое завершение сохраняются. Проверить это его реальными process-тестами; не возвращать прежний pipe deadlock.

Информационные log-детали ограничить 8 MiB на запуск, с явным счётчиком пропущенного; события переходов и ошибок не скрываются лимитом verbose. Локальный cache клиента — максимум 5000 записей / 4 MiB; более ранние данные читаются отдельными страницами. `+ N lines` считает скрытые загруженные строки, признак удалённого/ещё не загруженного хвоста показывается отдельно. История самого существующего progress не очищается косметической операцией.

Poll: record примерно раз в секунду, активный журнал/очередь раз в 2–3 секунды, архив реже; неактивные тяжёлые панели не опрашиваются. Один незавершённый poll на ресурс, bounded backoff после ошибок, явная свежесть данных. SSE/WebSocket пока не вводить: совместимый cursor API покрывает задачу и проще проверяется.

### 6. Воспроизведение

Предлагаемый backend нового TUI — отдельный управляемый `mpv --no-video` с JSON IPC и HTTP media API. [Официальный протокол](https://mpv.io/manual/stable/#json-ipc) описывает команды/наблюдение свойств и Windows named pipes. Запускать executable аргументами, не shell-строкой; заголовок авторизации передавать через локальное управление/защищённую конфигурацию, не query/argv/log. IPC доступен только текущему пользователю, конфигурация пользователя mpv и ненужные скрипты отключены.

Playback adapter управляет play/pause, seek, выбранным фрагментом и наблюдаемой позицией. Смена сессии останавливает прошлый источник; реплика/цитата использует одно и то же воспроизведение. Peaks запрашиваются через существующий API и масштабируются под ширину терминала; искусственная waveform не рисуется.

Использовать существующий process ownership pattern для собственного дочернего плеера, с graceful quit и ограниченным ожиданием/kill. Текущее синхронное `run()` не предназначено для долгоживущего IPC-плеера: добавить узкую lifetime-границу, покрытую process-тестами. Владение плеером не распространяется на демон. При отсутствии mpv preflight показывает способ установки; клиент в целом остаётся доступен, но playback-паритет не считается пройденным.

Альтернатива rodio/свой PCM-стример потребовала бы новой цепочки HTTP Range/seek/buffering/decoder и поддержки аудиоустройств клиента. Системный браузер/внешняя ссылка не выполняют требование управления плеером внутри TUI. Выбор mpv — предложение этого плана, зависимость явно входит в проверку поставки.

В ходе проверки 8.2 обнаружено, что прежний HTTP media собирал весь открытый Range
до ответа. Это противоречило выбранной проверке seek без полной предварительной
загрузки. Реализация использует ленивый `AudioStream` с PCM-окном до 1 MiB;
несколько окон не хранятся целиком. FLAC читается через supervised ffmpeg по интервалу:
input `-ss` с accurate seek и ограниченный `-t`, без whole-output decode чанка.
[Семантика seek FFmpeg](https://www.ffmpeg.org/ffmpeg.html) подтверждается отдельной
реальной проверкой сэмплов. Timeout 30s и output limit дополняют supervisor ownership.
Это не оценка общего RSS декодера и не изменение контрактов clip/смешивания.

### 7. Проверки и границы доказательств

- Чистые unit tests reducer/раскрытия/scroll/расчёта времени/редактирования, без сети, диска и sleeps; clock/ID фиксированы.
- Контрактные Rust/TS-тесты на общих JSON fixtures; отдельно авторизованный настоящий временный API с архивом в tempdir.
- Ratatui `TestBackend` + проверяемые снимки символов, стилей и cursor/focus на фиксированных размерах. [Официальный рецепт](https://ratatui.rs/recipes/testing/snapshots/) даёт базовый подход; текстовый снимок без стилей не ловит ошибки цветов.
- TUI process/e2e через PTY, на Windows через ConPTY: ввод, bracketed paste, resize, восстановление терминала, закрытие клиента при работающем демоне. Harness строится на готовой кроссплатформенной PTY-библиотеке, не на самописном разборе escape codes.
- Playwright для каждого раздела/действия UI и визуальных состояний. [Visual comparisons](https://playwright.dev/docs/test-snapshots) требуют одного окружения для эталонов: фиксировать browser/OS/fonts/viewport/clock, анимированные детали выключать или фиксировать. Baseline обновляется после просмотра diff, не автоматически в CI.
- Mock API проверяет детерминированный визуал и ошибки; E2E против временного настоящего сервера проверяет связывание маршрутов/артефактов. Ни один из них не объявляется проверкой качества ASR/LLM, микрофона или физического звука.
- Оба клиента обязаны пройти каждую строку [parity.md](parity.md). Специальные проверки playback отдельно подтверждают media/IPC; слышимость на реальном устройстве — отдельная Windows-приёмка. Плановая матрица требований — [evidence](evidence/coverage.md).

## Risks / Trade-offs

- RV-001/010 в настройках → фильтровать секретные/неизвестные значения в клиенте и исправлять сервер по принятому CFG-контракту отдельным узким fix; не объявлять Live по snapshot. Показ `.extra` из существующего UI не является требуемым паритетом утечки.
- RV-008/009/016, BL-002/004/021 → сохранить в общей evidence реальные пробелы. UI/TUI parity не означает их исправление. Если пробел блокирует конкретный приёмочный сценарий, change не считается реализованным до требуемого исправления/зависимости; молча исключать сценарий нельзя.
- Длинные журналы и медленный диск → bounded чтение, page/cache limits, коалесцирование heartbeat; измерить стоимость poll на большой синтетической истории, не на пользовательском архиве.
- Более одного writer журнала → определить единственного producer конкретного потока либо короткую межпроцессную блокировку append на файловой границе; проверить конкурирующее дописывание и целостность строк, не полагаться на случайную атомарность больших write.
- Новая runtime-зависимость mpv → проверяемая установка и transport/auth/IPC-тесты; не скрывать отсутствие backend успешным snapshot.
- Клавиши/Unicode/ширина терминала → тестировать реальные Windows Terminal/ConPTY, cell width, 16-color и ASCII. Версию Linux/macOS не объявлять проверенной по Windows-прогону.
- Расхождение двух клиентов → shared data fixtures, единая матрица действий и одинаковые сценарии ошибок; не пытаться делить React- и Ratatui-виджеты.

## Migration Plan

1. Добавить новый API/клиент/fixtures и отдельный бинарник, не меняя пользовательский запуск; снять проверяемые экраны на синтетических данных.
2. Реализовать новый TUI вертикальными срезами с тестами: archive/documents/journal → запись/очередь → notes/ask/search/settings → playback.
3. Применить journal-компоненты/токены в React и пройти все его действия/visual states. Сборка UI не заменяет browser QA.
4. Пройти P01–P30 в обоих клиентах, process/HTTP/PTY-тесты и Windows playback/recording приёмку. Известные блокирующие RV остаются видимыми зависимостями.
5. Включить `scripts/run.ps1 -Tui`, добавить новый binary в bundle/install. Перевести `--tui`/интерактивный launcher на нового клиента с одной локальной попыткой daemon-start и HTTP health/capability check в пределах 15 секунд.
6. После успешной проверки убрать старый TUI crate/старую engine-связанную ветку запуска и проверить feature flags/CI. Если проверка ещё не прошла, новый запуск не объявляется заменой старому и задачи остаются открытыми. Возврат при регрессии — предыдущий клиентский release с тем же обратно совместимым API; rollback не переписывает архив и не рестартует запись автоматически.
