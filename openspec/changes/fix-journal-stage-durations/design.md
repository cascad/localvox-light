# Design

## Context

См. proposal.md. Журнал ограничен страницами, поэтому первый видимый Running может
быть heartbeat посередине этапа. Progress уже содержит реальные границы текущей
попытки. У вложенных операций есть собственные elapsed_sec/start/end.

## Goals / Non-Goals

**Goals:** корректные часы этапа в журнале обоих клиентов при неполном хвосте,
отделение от вложенных операций, отсутствие выдуманного старта/нулевого времени.

**Non-Goals:** новый таймер в сервере, изменение persisted событий, дополнительное
сканирование журнала/HTTP-запросы, перезапуск обработки и восстановление неизвестных
границ старых попыток по косвенным признакам.

## Decisions

1. Group сохраняет operation ID: отдельная операция никогда не получает часы всего
   этапа. Только группа без operation ID использует соответствующий StageStatus.
2. Metadata подходит, только если непустой run совпал с execution.run, stage/state
   совпали. Для завершённого этапа его ended_at должен точно совпасть с at итогового
   события группы: так старой попытке не присваивается время новой с тем же stage.
   Для Running требуются реальное started_at и событие не раньше этого старта,
   отсутствие ended_at и подтверждённый активный этап; clock при потере связи не растёт.
3. Measured elapsed операции имеет приоритет. Иначе берутся её собственные start/end
   либо проверенные границы этапа. Некорректные/отрицательные/отсутствующие границы
   дают «время неизвестно». Первый heartbeat не используется как начало.
4. Положительное время менее секунды — `<1 с`; начиная с секунды сохраняется прежний
   minutes:seconds. Формат времени плеера не меняется. Нулевой measured elapsed остаётся нулём.

## Risks / Trade-offs

- Старый хвост без run или границ попытки → честное неизвестное время; данные другой
  попытки не подставляются. Восстановление произвольной старой истории вне scope.
- Разновременные progress/journal ответы → точное сопоставление конца и проверка
  принадлежности текущему интервалу; до совпадения время может оставаться неизвестным.
- Два клиента → одинаковые synthetic cases и проверки render/browser, без личного текста.

## Migration Plan

Обратно совместимый client-only change. Новые TUI и embedded UI собираются отдельно
от работающих экземпляров. Пользовательский архив не переписывается. Установка
заблокированного `.exe` ждёт штатного завершения соответствующего процесса.
