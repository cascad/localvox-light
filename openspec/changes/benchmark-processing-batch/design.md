# Design

## Context

См. proposal/Why. В bench уже есть WER/CER-инструменты, но нет воспроизводимого отчёта стоимости worker-фаз. Текущие release-бинарники старее изменений очереди. Доступны локальные GigaAM и публичные наборы bench; пользовательский архив для измерений не нужен. Progress хранит события этапов и операций, но не гарантирует отдельные границы загрузки модели, генерации и проверки.

## Goals / Non-Goals

Первый автономный срез — инструмент и контрольный release-прогон на явно выбранных PCM WAV. Полный BL-003 требует отдельно измерить координатор/очередь, длинную речь, настоящий summary и холодное/прогретое состояние моделей; инструментальный smoke этого не закрывает. Поведение продукта, модели, работающий демон и архив не изменяются.

## Decisions

- Добавить localvox-profile в существующий bench crate. Вход — JSON manifest локальных WAV PCM16 mono 16 kHz; пути относительно manifest, имена cases ограничены. Для каждого case/repeat создаётся новая изолированная сессия с копией аудио. Папка результата должна отсутствовать; существующая папка отклоняется до запуска.
- Последовательно выполнять реальные worker-фазы transcribe и опциональную summary через общий localvox-light-process: tree ownership, ограниченный вывод, deadline, фоновые приоритеты, Ctrl+C. Явные model-dir/endpoint/model, очищенное окружение, contained snapshot и отдельные TEMP/TMP предотвращают чтение пользовательской .env и неявный облачный provider. Summary допускает только loopback HTTP; прочие адреса отклоняются.
- Записать JSON checkpoint после каждого исхода: checksum бинарника/модели/аудио, платформа/число CPU, настройка фаз, порядок fresh-process repeats, длительности setup/phase/batch и реальный RTF. Результат не является замером полного координатора: queue_wait=null. Первый запуск не называем холодным запуском модели/дискового cache без отдельной процедуры.
- На Windows сохранять query handle worker от первого tick до завершения, опрашивать OS high-water marks каждые 20 ms и прочитать handle после выхода. Это наблюдаемый peak worker process, не всё дерево и не внешний Ollama; неизвестное — null с подписью, очень короткий пик может быть пропущен. На других ОС метрики ресурсов остаются unsupported, а не выдуманным нулём.
- Сохранить проверенные stage/operation durations из журнала, не суммируя вложенные операции и повторные события в общее время. Отсутствующие отдельные model-load/generation/verification границы оставить null. Ошибки/таймауты и частичный отчёт сохраняются; они не входят в успешные средние.

## Risks / Trade-offs

- Опасность затронуть архив → только новые каталоги, входное аудио не меняется, запуск без пользовательской .env, никаких удалений.
- Короткие записи не представляют двухчасовую встречу → маркировать контрольный набор, сохранить полный незавершённый критерий BL-003.
- Ресурсы родителя не равны дереву/LLM → явно указать scope и недоступные компоненты.
- Тест может принять отсутствие данных за ноль → проверки ошибок/пустых и повреждённых событий, resource handle после завершения, timeout и неизменность исходника.

## Migration Plan

Новая команда измерений и документация; миграция/перезапуск приложения не нужны. Сборка текущего release worker выполняется отдельно; не заменять установленный комплект и не останавливать чужие процессы.
