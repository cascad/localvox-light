# Контракты поведения и OpenSpec

Начинайте с [OpenSpec](openspec/README.md), [baseline](openspec/baseline.md),
[каталога](openspec/catalog.md) и [матрицы требований](openspec/evidence/coverage.md).

**`openspec/specs/` — принятый источник правды о требуемом поведении**, с 2026-09-27
по поручению владельца завершить инвентаризацию. Это не утверждение о соответствии
всего кода. Расхождения — в [review](openspec/review.md), проверки — в evidence,
работа — в changes. README/старые документы производные, контракт не переопределяют.
Исторические отчёты не задают текущий статус.

Для OpenSpec используйте официальные skills в [.agents/skills](.agents/skills),
CLI 1.13.2. Из корня репозитория: сначала `openspec list --json` и
`openspec list --specs`, для выбранного change — `status` и `instructions`.
Не правьте сгенерированные SKILL.md под проект.

- DEC-001–008 и запрет межсессионного узнавания приняты, повторно их не согласовывать.
  Нормативные требования распределены по capability; карта — в baseline.md.
- При баге сравнивайте вход/переход/артефакт с требованием и сценарием. Исправляйте
  реализацию; не переписывайте контракт под дефект. Новое намеренное поведение
  требует принятого change и delta, реализации и существенных проверок.
- Разделяйте статус контракта, состояние реализации и доказательства проверки.
  `accepted` не равно `implemented`, `code-reviewed` не равно `test-run`,
  найденный тест не равен пройденному, сборка не равна аппаратной приёмке.
- Каждое требование имеет стабильный ID, WHEN/THEN, ссылку на код и строку в
  evidence/coverage.md. Известный gap имеет RV или change и не исчезает после
  принятия спецификации. Непроверенные сценарии оставляйте непроверенными.
- Конкретные работы создавайте через `openspec new change`, артефакты — по
  `openspec instructions`. backlog.md — сырой inbox и указатель BL-ID.
  Proposal-only допустим; не придумывайте design/delta/tasks ради валидатора.
- `skip_specs: true` допустим для документации/инструментов/измерений без изменения
  поведения, не для скрытия будущих требований. BL-009 завершил аудит и однократное
  принятие baseline, а не реализацию всех известных пробелов.
- Не sync/archive невыполненные предложения как реализованные. Принятие baseline
  не закрывает их задачи; `isPlanningComplete` означает наличие документов.
- Сохраняйте F/PIPE/SC/BL/RV/ADR-ID. Не переписывайте исторические результаты как
  новые проверки. При изменении кода обновляйте доказательства затронутых требований.

Для документации: `openspec validate --specs --strict --no-interactive`,
`python scripts/check-openspec.py`, проверка diff. Для изменённого change также
запускайте его строгую валидацию. `validate --all` включает proposal-only черновики:
их ошибки показывайте отдельно, не выдавайте весь запуск за успешный.
Полный прогон моделей для правки документов не нужен. Проверяйте реализацию тестами
по риску изменения; не трогайте работающий демон/пользовательский архив ради аудита.
