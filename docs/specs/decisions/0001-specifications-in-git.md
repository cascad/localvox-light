# ADR-0001: контракты поведения рядом с кодом

Дата: 2026-09-27. Статус: принято для организации документации.
Источник: запрос владельца связать хотелки, реализованные функции и фактический код.

## Контекст

В репозитории уже есть реестр F1–F11, большой бэклог, пакеты работ, сценарии и чек-лист.
Их статусы и технические описания относятся к разным моментам. Галочка у выполненной
задачи не отвечает, что функция обязана делать сейчас и как доказать её исправность.
Есть пример: старые планы параллельного STT/SQLite не совпадают с текущей реализацией.

## Решение

Хранить действующие контракты, каталог, сценарии и открытые задачи в `docs/specs/`.
Сохранить существующие F-ID и исторические документы. Разделять решение, реализацию
и свидетельство проверки. Для правил PIPE указывать сценарии SC-PIPE, код и существующие
проверки; непокрытые правила явно отмечать. Ожидаемое поведение не выводить автоматически
из текущего кода. Важные изменения решений фиксировать отдельным ADR, заменяя ссылку,
а не переписывая причины старого решения задним числом.

Начать с Markdown и уже существующих Rust/интеграционных тестов. Добавить короткую
инструкцию для работы с репозиторием и шаблон PR. При необходимости использовать
GitHub Issues/Projects для планирования со ссылками на эти документы.

## Альтернативы и последствия

Один огромный README смешал бы контракт, историю и запуск. Только трекер задач не дал
бы версии контракта вместе с кодом. Полноценный Cucumber добавил бы слой определения
шагов, который сейчас не нужен для уже существующих проверок. ADR отдельно объясняют
выбор, но не заменяют ожидаемое поведение.

Цена выбранного решения: при изменении поведения нужно обновлять связи и свидетельства.
Markdown не выполняется автоматически, поэтому связь «правило → сценарий → тест»
поддерживается ревью; автоматизация этого контроля — [BL-010](../../../openspec/backlog.md#bl-010).
Наличие этого ADR не означает, что все функции уже прошли инвентаризацию.

Формат опирается на [описание ADR Майкла Найгарда](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
