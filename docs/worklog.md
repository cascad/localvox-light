## 2026-07-11 — Фаза A: фундамент качества

### WP-0.2 — Замер GigaAM: бюджет подтверждён, найден скрытый лимит
- **Проблема/идея:** прежде чем строить «отложенную качественную варку», нужно
  знать, сколько реально стоит час аудио на CPU. Ориентир конкурента (Summit):
  ~2 мин на час на M1.
- **Сделано:** замер на 18.5-мин русской лекции (yt-dlp → localvox-asr).
- **Проверено:** RTF 0.021 → час ≈ 75 с одним процессом, в 4 раза лучше нашего
  бюджета «≤5 мин» и лучше Summit — без всякой параллельности.
- **Сюжет:** первый прогон упал: `Broadcast 5000 by 27812` из недр ONNX. Оказалось,
  у GigaAM v3 позиционный контекст 5000 фреймов ≈ **200 секунд аудио максимум**, а
  наш батч-путь скармливал файл целиком — и никто этого не знал, потому что
  реалтайм-сегменты были по 10 секунд. Лимит, который нашёлся только потому,
  что мы дали модели 18 минут. Отсюда — оконный инференс в архитектуре варки.

### WP-A1 — Чанки: аудио перестало исчезать
- **Проблема/идея:** старый код удалял WAV сразу после распознавания — «сырьё»
  для переварки лучшими моделями терялось навсегда. Решение: непрерывная запись
  чанками + retention-политика (N дней), обработки только дополняют (P2/P3).
- **Сделано:** `core::chunks` — потоковый WAV-writer (flush ~5 c), ротация,
  meta.json, recovery `.part`, retention-sweeper, FLAC за флагом.
- **Проверено:** 10 юнит-тестов; живой тест: запись → `taskkill /f` → при
  следующем старте `.part` стал валидным WAV (ffprobe), потеря ≤ секунд.
- **Сюжеты (два):**
  1. Изначально я резал чанки по VAD-тишине «чтобы граница не попадала на слово»
     и городил нахлёст с дедупликацией. Владелец спросил: «а зачем вообще писать
     по паузам? писать можно кусками, склеивая». И это правильнее: **хранение —
     тупая ротация по времени** (PCM склеивается сэмпл-в-сэмпл), а семантика
     (окна по тишине) живёт на чтении, где она и так обязана быть из-за
     200-секундного лимита модели. Из writer'а выкинули VAD, кольцо нахлёста и
     три конфиг-параметра. Урок: не смешивать слой хранения со слоем смысла.
  2. Строгий тест непрерывности таймлайна упал на `1.0000000000000004 != 1.0` —
     f64-аккумуляция дрейфовала (в живом meta уже красовалось
     `41.503999999998975`). Таймлайн перевели на целые сэмплы (u64), секунды —
     только на выводе. Урок: время в аудио считаем в сэмплах, не в секундах.

### WP-A2 — Версии транскриптов
- **Проблема/идея:** «каждая обработка — новая версия, исходник неприкосновенен»
  должно быть механикой, а не дисциплиной. Плюс перезапускаемость джобов.
- **Сделано:** `core::versions` — versions.json (модель/параметры/метка/родители/
  best), **двухфазная запись**: выделить id → записать файл → атомарный commit;
  файл без записи в манифесте = мусор упавшего джоба, безопасно перезаписывается.
- **Проверено:** 7 юнит-тестов (дубликаты id, битый манифест → пустой, reload).
- **Сюжет:** идемпотентность «рестарт без дублей» получилась бесплатно из
  двухфазности — никакого журнала транзакций, только порядок операций и rename.

### WP-A3 — Варка: качество фоном, черновик мгновенно
- **Проблема/идея:** F8 «двухскоростной конвейер» — fast lane только для
  wake-word и live-индикации, качество делает отложенная варка.
- **Сделано:** `core::cook` — Windower (окна ≤180 c по VAD-тишине поверх
  склеенного потока, классификатор инжектится — тестируется без ONNX) + прогон
  GigaAM → версия jsonl с таймкодами; бинарь `localvox-process` (recovery,
  идемпотентность, `--force`).
- **Проверено:** e2e на живых сессиях: 174 c за 5.1 c (RTF 0.029); пустая
  сессия → 0 строк; повторный запуск пропускает готовое.
- **Сюжет:** варка сознательно **не читает meta.json** — список чанков строится
  сканом имён файлов, потому что склейка непрерывна by design. Это сделало её
  устойчивой к сессиям после падения (где meta неполон) в тот же день, когда
  такая сессия реально появилась в тестах. И бонус наблюдение: во время теста
  владельца в loopback играл ролик про НПЗ — распознался с пунктуацией и прямой
  речью, случайно став первым настоящим демо.

### WP-A4 — LLM-обработка и сага про thinking
- **Проблема/идея:** протокол встречи и чистка транскрипта через локальный LLM;
  один клиент на всех провайдеров (OpenAI-compatible = Ollama/OpenAI/OpenRouter).
- **Сделано:** крейт `localvox-light-llm`: клиент (sync, ureq), глоссарий
  (детерминированные замены по границам слов + ambiguous-подсказки в промпт,
  лог замен), шаблоны-файлы, map-reduce, `--summary/--cleanup`.
- **Проверено:** 11 юнит-тестов; e2e: cleanup 9.4 c, summary 17.5 c
  (qwen3.5:9b) — структурированный протокол, пустые разделы честно помечены.
- **Сюжет (лучший для паблика):** первые summary.md пришли **пустыми** после
  4 минут работы модели. Расследование: Qwen3.5 через OpenAI-endpoint Ollama
  уходит в reasoning, `think:false` и `/no_think` там игнорируются, а
  `max_tokens` режет размышления и ответ **вместе** — модель думала до упора и
  на ответ токенов не оставалось. Причём размышления Ollama возвращает отдельным
  полем `reasoning`, которое OpenAI-клиенты просто не читают. Лечение: нативный
  `/api/chat` с честным `think:false` — **0.5 секунды вместо минут**. Клиент
  теперь автоматически выбирает диалект по `:11434`. Урок: «OpenAI-compatible»
  у локальных серверов — это про форму JSON, а не про поведение.

### WP-A5 — Один конвейер для всего аудио
- **Проблема/идея:** YouTube/файлы жили отдельным миром с plain-text выводом;
  должен быть один формат сессий для всех источников (+ сценарий S4 «конспект
  видео одной командой»).
- **Сделано:** `--ingest <URL|файл>` → сессия с чанками → общий конвейер;
  экспорт `--export txt|md|srt`; общий `TranscriptLine`; шаблон
  `video-notes-ru` + `--summary-template`.
- **Проверено:** e2e: 18.5-мин лекция про Обломова → варка 26.6 c → md+srt →
  конспект с таймкодами за 29.7 c (map-reduce: 2 части + свёртка). 75/75 тестов.
- **Сюжет:** вся обработка 18 минут видео — меньше минуты на локальном железе,
  и из этого меньше половины — LLM. «Конспект любого видео одной командой» —
  фича, которой нет ни у Summit, ни у Granola, ни у Meetily.

## 2026-07-11 — Фаза B: интерактив (начало)

### WP-B3 — Слоты и интеграции: куда падают заметки
- **Проблема/идея:** голосовому «запиши в идеи…» нужен бэкенд назначений.
  Первая версия обросла терминологией и показалась владельцу переусложнением —
  переработали в тот же день: **слот = только голосовое имя** («запиши в слот
  такой-то» — остаётся), под ним простой интерфейс `Integration` с двумя
  адаптерами: `files` (файл → append-строки; папка → md-файл на заметку) и
  `mcp` (универсальный мост в любой MCP-сервер — Obsidian-MCP, Notion, без
  написания отдельных интеграций; вытащен из фазы C).
- **Сделано:** крейт `localvox-light-integrations` (без зависимости от core —
  P5): реестр `slots.toml`, оба адаптера, минимальный MCP-клиент на stdio
  (~150 строк: initialize → notifications/initialized → tools/call, ndjson);
  CLI `localvox-note`; how-to `docs/integrations.md`.
- **Проверено:** 5 тестов, включая **живой MCP-e2e**: фейковый MCP-сервер на
  Python принимает tools/call и пишет заметку в файл; плюс e2e обоих режимов
  files. 84/84 по workspace.
- **Сюжеты:** (1) TOML не разрешает кириллицу в bare-ключах — `[slots.идеи]`
  падает парсером, надо `[slots."идеи"]`. (2) Git Bash-пути в конфиге:
  `/c/Users/…` Windows превращает в `D:\c\…`. (3) Windows-Python читает stdin
  в cp1251 — UTF-8 JSON приезжает суррогатами, лечится `python -X utf8`;
  три локали-граблей за один пакет работ. (4) Весь «универсальный мост в любую
  интеграцию» — это 150 строк stdio-клиента, потому что MCP по сути ndjson
  JSON-RPC.

### WP-B2 — Голосовое «запиши»: продукт заговорил
- **Проблема/идея:** главный дифференциатор (ни у Summit, ни у Granola голосового
  интерактива нет): сказал «запиши в идеи попробовать сортформер» — заметка в
  Obsidian, ассистент подтвердил голосом. Ограничение v1: детект на
  финализированных сегментах (задержка ≈ пауза VAD + ASR), не на партиалах.
- **Сделано:** `TranscriptHook` в ядре (одна точка входа после append, вызов из
  ASR-воркеров неблокирующий — отправка в канал); крейт `localvox-light-voice`:
  `Brain` — чистая state-machine (парсер грамматики, pending-режим, анти-эхо),
  исполнение Action'ов в своём потоке; TTS SAPI/Piper. Модуль сам включается
  при наличии slots.toml, выключается env'ом.
- **Проверено:** 10 юнит-тестов Brain (мультисловные имена слотов, алиасы,
  «голое имя ≠ адрес», pending с таймаутом, кастомный триггер, эхо-фильтр
  фрагментов TTS) + e2e хук→файл; 94/94 по workspace; поверх — адверсариальное
  мульти-агентное ревью (4 измерения). Живая приёмка с микрофоном — отдельно.
- **Сюжеты:** (1) дизайн-решение: «запиши идеи проекта» НЕ уходит в слот
  «идеи» — голое имя слота внутри речи не считается адресом, только «в идеи»/
  «в слот идеи»; иначе ложные маршрутизации на каждом втором предложении.
  (2) Анти-самозахват: ассистент слышит собственный TTS микрофоном; фильтр по
  «последней произнесённой фразе» пришлось учить фрагментам — VAD режет фразу
  из колонок на куски. (3) Текст в PowerShell передаём файлом, не аргументом —
  третья встреча с Windows-кодировками за день.

### WP-B2b — Адверсариальное ревью голосового контура: 21 находка, 12 фиксов
- **Проблема/идея:** свежий интерактивный код с потоками, внешними процессами и
  акустической петлёй — идеальная мишень для мульти-агентного ревью
  (4 независимых измерения × адверсариальная верификация каждой находки).
- **Сделано/Проверено:** 27 агентов, 23 находки, 21 подтверждена верификаторами,
  12 исправлено сразу (остальные — в план с пометками): шардирование ASR-пула по
  источнику; recovery не реплеит команды; drain голосовой очереди на выходе;
  MutexGuard-скоуп; эхо-петля; фильтр междометий в pending; «Не знаю слот X»;
  MCP-таймаут + reader-поток + `.cmd`-шимы + фильтр встречных запросов;
  portable-путь slots.toml; уникальные temp. Все 97 тестов зелёные после фиксов.
- **Сюжеты (золотая жила):**
  1. **Эхо-петля**: подтверждение «Записал в идеи: купить молоко» микрофон
     слышит из колонок, Vosk промахивается в одном слоге — «ЗАПИШИ в идеи
     купить молоко» — и ассистент… снова пишет заметку и снова подтверждает.
     Вечный двигатель заметок. Лечение двухслойное: подтверждаем словом
     «Готово» (акустически не похоже на триггер) + эхо-фильтр по пересечению
     токенов ≥80% с последней TTS-фразой.
  2. **Гонка порядка**: при двух ASR-воркерах короткая фраза обгоняет длинную —
     Brain видел заметку раньше команды. Фикс — шардирование сегментов по
     источнику: mic всегда обрабатывается одним воркером строго FIFO, а mic и
     loopback по-прежнему параллельны.
  3. **Машина времени**: recovery при старте догоняет вчерашние WAV — и
     вчерашние «запиши…» исполнились бы заново, роботом, при включении
     компьютера. Один флаг `from_recovery` в событии сегмента.
- **Бизнес-смысл ревью:** три high-бага такого класса на живом голосовом
  ассистенте = потерянное доверие пользователя с первого дня.

### WP-B2c — Первый живой диалог: «кажется, нифига не происходит»
- **Проблема/идея:** владелец сказал ассистенту пять фраз — и решил, что ничего
  не работает. На деле **всё работало**: две заметки честно лежали в vault. Но:
  «запиши в идеей» (падеж!) и «запиши в день» (нет такого слота) ушли текстом в
  default-слот, «запомни»/«отметь мысль» были закомментированы в конфиге, а
  статус модуля жил только в stderr, который TUI прячет. Классика: работает ≠
  видно, что работает.
- **Сделано:** (1) морфология-lite в матчере адресов — совпадение по общему
  префиксу (стему): «в идею/идеей» → слот «идеи», «в работу» → «работа», при
  этом «в день» на «идеи» не матчится; (2) статус голосового модуля — в
  Debug-панель TUI и в stderr при старте («активаторы [...] · слоты: ... ·
  TTS ...»); (3) активаторы «запомни» (→идеи) и «отметь мысль» (→входящие)
  включены в конфиге владельца.
- **Проверено:** 98/98 тестов (новые: падежные формы матчатся, «в день» — нет);
  живая перепроверка — за владельцем после перезапуска exe.
- **Сюжет:** обратная связь — это фича №0 голосового интерфейса. Пользователь
  не видит файловую систему в момент речи; если ассистент молчит и некуда
  посмотреть — для человека это «не работает», даже когда всё записано.

### WP-B1 — Сегменты в RAM: очередь из 74 WAV исчезла как класс
- **Проблема/идея:** владелец увидел «Очередь WAV: 74 шт.» и справедливо спросил,
  где обещанные крупные куски. Крупные чанки уже писались — но параллельно
  черновой fast-lane по-прежнему сыпал короткие VAD-сегменты на диск (наследие
  до-чанковой durability). Раз чанки — первичный артефакт, черновику диск не
  нужен вовсе.
- **Сделано:** `SegmentPayload::Ram|Disk` — сегменты идут в ASR прямо из памяти;
  дисковый режим остался legacy-флагом; recovery старых WAV прошлых запусков
  работает (Disk-payload); счётчик очереди для TUI — живой атомик вместо
  подсчёта файлов.
- **Проверено:** 101/101 по workspace; новые тесты: RAM-режим не создаёт ни
  одного файла, disk-legacy пишет как раньше, discard на паузе чистит без следа.
- **Сюжет:** приятный каскад от смены точки зрения «что здесь источник истины»:
  как только истиной стали чанки, у чернового контура отвалились запись на диск,
  удаление после ASR, recovery-переочередь и весь феномен «очередь WAV» из TUI.
  Минус целый класс состояния — вот что даёт правильная иерархия данных.

### WP-B2d — Конец заметки и живая индикация
- **Проблема/идея:** владелец после первого дня использования: «не понимаю, как
  ты понимаешь, что надо закончить писать» + «нет индикации, что запись
  идёт/остановилась». Конец заметки был равен концу VAD-сегмента (пауза 0.8 с) —
  обрывал мысль на вдохе и был невидим.
- **Сделано:** многосегментный захват (реестр F2 «пауза-тишина и/или
  стоп-слово»): текст копится фразами; конец — стоп-слово отдельной фразой
  («всё»/«конец»/«стоп», конфигурируемо), тишина 3.5 с, новая команда или 90 с
  максимума. Живая индикация в статус-строке TUI: «● заметка [идеи]: 2 фразы…»
  → «✓ записано в [идеи]: …». TTS во время диктовки молчит (перебил бы запись),
  «Готово, записал…» — по закрытии. Brain получил tick-таймеры; воркер — цикл с
  recv_timeout и финальный flush открытой диктовки при выходе.
- **Проверено:** 12 тестов Brain переписаны под новую семантику (стоп-слово не
  входит в текст; idle-tick склеивает фразы; новая команда закрывает старую;
  отмена пустого ожидания; сохранение открытой заметки при shutdown). 99/99.
- **Сюжет:** «когда заканчивается мысль» — главный незаметный вопрос голосовых
  заметок. Пауза дыхания ≠ конец мысли; ответ — комбинация явного жеста
  (стоп-слово), терпеливой тишины и здравых лимитов, плюс постоянная индикация,
  в каком состоянии машина. Ровно то, что владелец сформулировал с первой
  попытки использования.

### WP-B2e — «Запиши это»: ретро-захват без ring-буфера
- **Проблема/идея:** киллер-фича из бэклога — мысль уже прозвучала (твоя или
  собеседника), повторять вслух неудобно. План предполагал аудио-ring-буфер +
  LLM-выжимку; оказалось, буфер не нужен вовсе.
- **Сделано:** кольцо последних ФРАЗ (не аудио!) в Brain — fast-lane и так
  непрерывно транскрибирует оба канала; хук теперь отдаёт голосовому модулю и
  loopback (только как контекст — команды из колонок по-прежнему не работают);

### WP-C6 — Ambient-сессионизация: демон режет сутки на встречи
- **Проблема/идея:** всегда-включённый демон (фаза C — Ambient) пишет
  непрерывно. Без сессионизации это ОДНА бесконечная сессия — варить,
  суммировать и искать по ней бессмысленно. Нужно резать поток на
  осмысленные единицы: звонок = сессия, длинные простои — граница.
- **Сделано:** пайплайн стал владельцем жизненного цикла сессии. Детект
  звонков шлёт ему сигналы (началась/кончилась встреча), пайплайн открывает
  под звонок отдельную сессию с pre-roll: последние 15 с «до» детекта берутся
  из кольцевого буфера — Windows обновляет реестр микрофона не мгновенно,
  поэтому без pre-roll начало «алло, привет» потерялось бы. Разрез ambient по
  длинной тишине. Побочно закрыта старая претензия ревью: раньше detect писал
  meta.json параллельно с рекордером (два писателя) — теперь писатель ОДИН.
- **Проверено:** 126 тестов (+3 сессионизации). Нашёлся и починен реальный
  баг: быстрые ротации в пределах секунды давали одинаковое имя каталога
  (timestamp до секунды) → сессии затирали друг друга; добавил суффикс -2/-3.
- **Сюжет:** pre-roll — признание, что детектор всегда опаздывает. Мы узнаём
  о звонке через секунды после его начала, но пишем-то непрерывно — значит
  «прошлое» уже на диске, надо лишь прихватить его в новую сессию. Детектору
  не нужно быть быстрым, если запись никогда не выключается.

### Ревью WP-C5 — 11 агентов против веб-поверхности
- **Проблема/идея:** веб-страница + браузерный доступ открывают новый класс
  угроз (CSRF, XSS, DNS-rebinding), которого у консольного инструмента не было.
  Прогнали 2 измерения (web-security + correctness), каждую находку — скептику.
- **Сделано:** 9 находок, 7 подтверждено. Главное (high): дефолтный демон
  127.0.0.1:3017 без токена доверял ЛЮБОМУ loopback-запросу — значит любой
  сайт в браузере жертвы мог через fetch писать заметки в vault и (через
  DNS-rebinding) выкачивать расшифровки. Закрыто проверкой Host/Origin: без
  токена принимаем только loopback-Host и loopback-Origin (перевязанный Host
  = evil.com → 403, cross-origin POST → 403). XSS-класс снят в корне: имена
  сессий больше не интерполируются в JS-строки onclick — карточки несут
  data-атрибут, клик ловит один делегированный слушатель, имя ставится через
  textContent. Плюс CSP (connect-src 'self' — токен из localStorage наружу не
  утечёт), Cache-Control, X-Content-Type-Options, константное сравнение
  токена, таймаут fetch (телефон не залипает в «загрузка…»), нормализация
  0.0.0.0→127.0.0.1 для кнопки трея, is_enabled сверяется с текущим exe
  (после переезда бинаря галка не врёт), пункт «Открыть веб-архив» только
  если API реально поднялся.
- **Проверено:** 123 теста; live curl — CSRF-Origin/DNS-rebind Host → 403,
  легитимный loopback → 200, CSP-заголовки на статике.
- **Сюжет:** локальный API на 127.0.0.1 — не «доверенная зона»: браузер
  жертвы дотянется до него с любого сайта. «Только localhost» без проверки
  Origin/Host — это открытая дверь, а не защита.

### WP-C7 — Автоварка: секретарь доваривает сам
- **Проблема/идея:** до сих пор варка (chunks → транскрипт) запускалась руками
  через `localvox-process`. Для «секретаря на автопилоте» (выход фазы C) демон
  должен доваривать сам — в фоне, по мере закрытия сессий.
- **Сделано:** durable-очередь джобов (`jobs.json`, atomic tmp+rename) + поток-
  планировщик в демоне. Discovery: сессии с аудио, без транскрипта, «тихие»
  (никто не пишет ≥60 с) — их и варим. Выполнение — subprocess `localvox-process`
  (ядро остаётся без ONNX/ort, «отчуждаемость»). At-least-once: `Running` при
  падении процесса → снова `Pending`; варка идемпотентна (версия с меткой
  пропускается). Лимит попыток — сломанную сессию не долбим вечно.
- **Проверено:** 133 теста (+5 очереди/discovery); варка идемпотентна (уже
  проверена e2e ранее).
- **Сюжет:** «файловая система как очередь» соблазнительна (сессия без версии
  = надо сварить, localvox-process идемпотентен) — но она не помнит, что
  что-то СЛОМАЛОСЬ: битую сессию сканер находил бы вечно и варил в цикле.
  Явная очередь с cap попыток нужна именно ради памяти о неудачах, а не ради
  памяти о работе.

### WP-C9 — Причёсанный транскрипт как версия
- **Проблема/идея:** «тщательная варка» (заявленный козырь против Summit) до
  сих пор давала либо сырой ASR, либо processed.md-прозу (теряет таймкоды,
  не ищется построчно, не играется). Нужен причёсанный транскрипт КАК версия:
  исправленный текст, но те же таймкоды и реплики → best → поиск/плеер/экспорт
  берут его автоматически, сырой цел и переключаем.
- **Сделано:** refine_session — построчная LLM-правка с нумерацией [N].
  Каждую реплику исправляем, но структуру (source/start/end, число и порядок
  реплик) держим жёстко: LLM возвращает те же [N], parse собирает по номерам,
  непришедшие/пустые остаются оригиналом. Результат — новая версия refined
  (parents=[best]) и новый best. Плюс CLI версий (list/set-best) — давно
  висевший хвост.
- **Проверено:** unit на parse_numbered (терпит мусор/переносы) + 139 workspace;
  живьём на реальной лекции (Ollama qwen3.5:4b): 7→7 реплик, таймкоды
  побитово те же, 3 исправлены, set-best v1↔v2 работает.
- **Сюжет:** соблазн был отдать LLM весь транскрипт и взять что вернёт — но
  тогда таймкоды и границы реплик превращаются в кашу. Дисциплина «правь текст,
  не трогай структуру» + нумерация реплик + fallback на оригинал делают
  ненадёжный LLM безопасным: худшее, что он может — не улучшить реплику, но
  не потерять и не сдвинуть её. Плеер и поиск это ценят больше, чем красоту.

### Ревью WP-C9 — 9 агентов: как ненадёжный LLM всё же теряет реплики
- **Проблема/идея:** refine держится на дисциплине «правь текст, не структуру».
  Ревью проверило, где эта дисциплина протекает под ненадёжным LLM. 7 находок,
  1 ложная (неатомарность commit+set_best — best() падает на max-id, повтор
  чинит сам).
- **Сделано:** главная (high) — номера реплик глобальные, а батч видит только
  свой срез; если LLM переномеровал ответ с [1] (вместо [81]), правки батча-2
  затирали реплики 1..40 батча-1 (плеер показал бы чужой текст на чужом
  таймкоде). Фикс: принимаем только номера, реально отправленные в этот батч.
  Ещё: перенесённая LLM на две строки реплика теряла хвост → склейка
  продолжений; идемпотентность протекала при переключённом на сырой best
  (плодила дубль-refined) → переиспользуем существующего потомка; refine и
  set-best писали versions.json без `.cook.lock` → та же гонка two-phase commit,
  ради которой лок и заводили; добавлен счётчик «без ответа LLM» (3/40 исправлено
  выглядело одинаково и когда правок не нужно, и когда модель проглотила 37).
- **Проверено:** 140 тестов (+склейка переносов, +скип преамбулы); живьём —
  idempotency при best=v001+потомок переиспользует v002, v003 не плодит.
- **Сюжет:** дисциплина «не трогай структуру» защищает от искажения, но не от
  ПОТЕРИ: LLM, переномеровавший или перенёсший реплику, обходит нумерацию с
  фланга. Защита — не доверять номерам ответа глобально, а сверять с тем, что
  реально спросили в этом батче. Граница батча — это и граница доверия.

### Ревью WP-C13 — 9 агентов: «мелочи» умеют сдвигать весь таймлайн
- **Проблема/идея:** пакет хвостов выглядел безобидно — но три из семи правок

### Ревью WP-C12 — 12 агентов: ffmpeg молчит о битом, sweep ест встречи
- **Проблема/идея:** WP-C12 трогает первичные данные (sweep УДАЛЯЕТ каталоги)

- **Сюжет:** инструменты по умолчанию прощают — и это яд для конвейеров.

  всегда включай строгий режим (-xerror) и показывай stderr: конвейер должен
  предпочитать громкую смерть тихой лжи.

- **Сюжет:** доступность аудио-устройства — не бинарная: «есть, но молчит» —

### WP-C14в — «Рецепт варки»: как чуть не починили только новые сессии
- **Проблема/идея:** ревью задало вопрос, который мы себе не задали: а доедет ли
  новый дефолт окон до УЖЕ сваренных сессий? Не доезжал. Варка пропускала
  сессию, если версия с меткой `gigaam-int8` уже есть, а автоварка считала
  сваренной любую сессию с best-версией. То есть весь существующий архив
  навсегда остался бы с «кашей», а исправление касалось бы только записей,
  сделанных после апдейта. Самый неприятный класс багов: фикс есть, а пользы нет.
- **Сделано:** в `params` версии пишется **рецепт** — `метка/w30-c15-s500`.
  Сессия, сваренная другим рецептом (или без него — то есть до WP-C14),
  переваривается ровно один раз. `JobQueue::requeue_stale` пробивает дедуп по
  имени сессии (иначе `Done`-джоб запирал переварку навсегда), варка переставляет
  `best` на себя — иначе указатель остался бы на `refined`, построенном от старой
  «каши», и поиск с экспортом продолжали бы отдавать мусор.
- **Проверено:** живьём на приёмочной сессии — сваренная старым рецептом
  переварилась (v004), повторный запуск ушёл в пропуск (идемпотентность цела),
  `best` переехал на свежую варку. Тесты: `discovery_recooks_session_cooked_with_stale_recipe`
  (три сессии — старый рецепт / без рецепта / текущий), `requeue_stale_revives_done_job_but_not_running_one`.
- **Сюжет:** «рецепт» в манифесте версии — это дешёвый способ сделать архив
  самообновляемым: любое будущее изменение варки (окна, VAD, версия модели)
  автоматически прокатится по всем сессиям, потому что расхождение рецепта и есть
  сигнал «переварить». Мы получили миграции без миграционного фреймворка.

### WP-C16 — Секретарь, который выдумал встречу
- **Проблема/идея:** на приёмке владелец открыл протокол сессии, где он просто
  напевал. В протоколе: «Основные темы: обсуждение планов на неделю», «Поручения:
  Иван → обновить React-компонент → до пятницы», «Мария → перенести логику в API»,
  «задач в бэклоге больше 150». В записи не было НИ ОДНОГО из этих слов.
- **Разбор:** каждый выдуманный факт — строчка нашего же глоссария
  (`capacity` → «как посетит», `Jira` → «жира», «диаграмма Ганта» → «кант»).
  Глоссарий подставлялся в промпт ЦЕЛИКОМ через `{{glossary}}`, а расшифровка
  была пустой («Т.»). Единственная защита — `transcript.trim().is_empty()` — её
  не ловила. Модели 4B не за что было зацепиться, и она приняла список терминов
  за содержание встречи. Мы сами вручили ей материал для галлюцинации.
- **Сделано (три рубежа):** (1) **порог речи** — меньше 30 значимых слов → LLM
  не вызывается вообще; (2) **глоссарий по вхождению** — в промпт уходят только
  термины, реально звучавшие в записи; (3) промпт: запрет выдумывать + правило
  «нет ни одной законченной фразы → одна строка отказа».
- **Проверено:** та же сессия, тот же промпт → `llm: пропущено — речи слишком
  мало (1 слов, нужно ≥ 30)`. Выдуманные протоколы тихих сессий удалены.
- **Сюжет:** самый опасный баг продукта — не падение, а уверенная ложь.
  Транскрипт с ошибками пользователь перепроверит; протокол с поручениями
  «Ивану до пятницы» он перешлёт команде. И виноват был не «глупый 4B»: мы
  требовали от модели «не выдумывай», а затем давали ей пустоту и приказ
  «составь протокол». Это противоречие, и модель разрешила его не в нашу пользу.

### WP-C16в — Порог по длине был костылём (замечание владельца)
- **Проблема/идея:** владелец забраковал первую заплатку: «а если там мысль
  будет, или короткий звонок?». И он прав: порог «меньше 30 слов → не звать LLM»
  защищает от тишины ЦЕНОЙ ровно того, ради чего продукт существует. «Отметь
  мысль: переписать варку на пул воркеров» — восемь слов и самое ценное, что
  скажут за день. Порог мерил не то: опасна не краткость, а безосновательность.
- **Сделано:** порог по длине выброшен. Вместо него:
  (1) **`grounding.rs`** — детерминированная проверка ответа по расшифровке:
  каждое имя, число, латинское слово обязано опираться на запись. Не опирается →
  модели предъявляют выдуманные слова и дают ОДИН шанс переписать; настаивает →
  результат не сохраняется. Починка ASR-искажения («XI от И» → «XAI») отличается
  от выдумки по фонетической близости; числа не чинятся вовсе и сверяются с
  записью цифрами ИЛИ словами («150» ↔ «сто пятьдесят», через `num2words`).
  (2) **Форма ответа следует за входом** — шаблон `note-ru` (выжимка в 1–3 фразы)
  для короткой записи вместо протокола с разделами «Решения» и «Поручения»:
  схему, которую велено заполнить, модель заполнит — выдумкой, если нечем.
  Ошибка в выборе формы теперь безопасна: выдумку ловит проверка.
  (3) Остался ровно один порог, и он не эвристика, а факт: ноль распознанных слов.
- **Проверено:** синтетическая сессия с одной мыслью → `note-ru` → «Предложено
  переписать варку на пул воркеров, чтобы избежать переполнения процессора.»
  Мысль ВЫЖИЛА и осталась обоснованной. Выдуманный протокол (тот самый, с
  Иваном и «150 задачами») проверку не проходит — ловится по числам и латинице.
- **Слепое пятно, зафиксировано тестом:** кириллическое имя первым словом пункта
  списка («* Иван → …») как имя не ловится — отличить его от «Компания» в начале
  предложения нечем без словаря имён. Первым же кандидатом в «выдумку» у меня
  стала именно «Компания»: проверка, бракующая честный текст, хуже отсутствующей.
  Такие протоколы всё равно не проходят: сроки, числа и латиница проверяются
  независимо от позиции.
- **Сюжет:** правильная защита проверяет РЕЗУЛЬТАТ, а не отсекает вход по
  косвенному признаку. Порог по длине — это отказ от работы там, где работа
  нужнее всего; проверка обоснованности — это работа с проверкой. Первое дёшево
  и хрупко, второе дороже на один вызов модели в редком случае и не зависит от
  того, какую модель подсунут завтра.

### WP-C17 — Демон перестал глотать вывод варки
- **Проблема/идея:** варка идёт в отдельном процессе (`localvox-process`), и его
  stdout/stderr никто не читал. Владелец не увидел строку «переварка: сварена
  другим рецептом», а вместо причины падения LLM в `jobs.json` попадало голое
  «exit 2». Диагностика была, но не доезжала.
- **Сделано:** демон перехватывает вывод ребёнка (`Stdio::piped`) и переливает
  построчно в свой лог (`варка[<сессия>]: …`); хвост stderr копится, и самая
  содержательная строка («ошибка …», «LLM выдумала …») идёт в `last_error` джоба
  — то есть видна и в `/api/jobs`, и в вебе. Потоки-качалки джойнятся после
  завершения ребёнка: без этого терялись последние строки, а там как раз ошибка.
- **Проверено:** ребёнок с несуществующей моделью печатает внятное «ошибка llm:
  Ollama-запрос … HTTP 400», а не молчит. (Проброс в лог демона проверен кодом,
  живьём — на следующей приёмке: демон пишет микрофон.)

### WP-C20б — «Пусто» определяем фактом, а не формулировкой
- **Проблема/идея (владелец):** «Мне не нравится подход, что мы должны искать
  текст про не распознан. Есть прям железобетонный вариант определить, что там

  это гадание по формулировке, которую модель вольна менять.
- **Сделано:** признак — **нулевое пересечение содержания**. Настоящий разбор

  сама. Опознавать надо по следам, которые подделать нечем: разбор записи

  докричаться из HTTP-потока до пайплайна записи), а в `meta.json` остаётся след:

- **Слоты — выбор из настроенных**, а не свободный ввод: опечатка в имени молча
  уводила заметку в слот по умолчанию, и человек не понимал, куда она делась.
  Плюс подсказка, где эти файлы лежат.
- **Протокол стал нейтральным.** Разделы «Решения / Поручения / Риски» — это про

- **Варка стартует за 20 с, а не за 5 минут.** Опрос — это скан каталога и чтение
  jobs.json, копейки. Пять минут ожидания человек воспринимает как «не работает»,

- **Сюжет:** обвинить модель было проще всего, и владелец уже собирался менять её.

### WP-C29 — Нарезка по фразам выброшена: таймкод не должен быть догадкой

  может выплюнуть кусок слова далеко от места, где оно звучит. Вчера я «починил»

- **Сюжет:** я дважды чинил симптом и оба раза ломал в другую сторону. Владелец

  улучшением: конструкция, в которой ошибка невозможна, лучше конструкции, в
  которой ошибку научились ловить. Плюс WER улучшился.

### WP-C31 — Сваренная сессия без протокола: дыра в discovery
- **Проблема (владелец):** «Расшифровка и так лежит. Протокола нет, читаемого
  текста — нет. Какого хера? В логах тоже ничего нет».
- **Разбор:** автоварка спрашивала только «нужна ли ВАРКА». Сессия, сваренная

  джоба никто не создаёт → LLM-часть не запускается. Никогда.
- **Сделано:** `sessions_needing_artifacts` — «расшифровка есть, протокола нет».
  Защита от вечного цикла: возвращаемся к сессии, только если раньше её
  обрабатывали БЕЗ этих флагов; если флаги стояли, а файла нет — значит, делать

- **Плюс:** демон больше не молчит. Молчащий демон неотличим от сломанного —
  раз в минуту в лог идёт «очередь пуста, все сессии обработаны».

### WP-C32 — «Выдуманное число 9», которого не было нигде
- **Проблема:** честный протокол уехал в карантин с вердиктом «числа: 9», хотя

  из задач»).
- **Сделано:** складываем только по правилам русского счёта — разряды внутри
  числа обязаны УБЫВАТЬ (сотни → десятки → единицы). Два числительных одного
  разряда подряд — это ДВА числа: «четыре пять» → 4 и 5. «Один» отдельным словом
  числом не считается, но в составе («двадцать один», «одна тысяча») работает.
- **Проверено:** та же сессия — протокол прошёл проверку и лёг обычным
  `summary.md`, без карантина.
- **Сюжет:** третий раз за два дня «модель выдумала» оказывалось «проверка

### WP-C33 — Журнал обработки: «сделано» перестало быть догадкой
- **Проблема (владелец):** «Статус окончания обработки — это наличие всего что
  нужно. Почему мы можем попасть в вечный цикл? Давай хранить мету явно».
- **Разбор:** статус выводился из НАЛИЧИЯ ФАЙЛА, а это двусмысленно: нет
  `summary.md` — значит «ещё не делали» ИЛИ «делали, но делать было нечего».
  Из двусмысленности я выкручивался эвристиками («а стояли ли тогда флаги?»), и
  каждая ошибка в них давала либо вечный цикл, либо навсегда потерянный протокол.
  Оба варианта мы на приёмке и получили.
- **Сделано:** `processing.json` в каталоге сессии — `артефакт → {рецепт, исход,
  когда}`, исход ∈ `ok` / `nothing` / `unverified` / `failed`. Нет записи → делать;
  другой рецепт (сменилась модель/шаблон/версия промпта) → переделать; та же
  запись, чем бы ни кончилась, → не трогать. **Вечный цикл невозможен по
  построению, а не по бдительности.** `failed` повторяется темпом очереди.
- **Почему не sqlite (как предлагал владелец):** всё о сессии живёт в её каталоге —
  каталог можно скопировать на другую машину, и он самодостаточен (P5). Общая БД
  стала бы третьим хранилищем состояния и рассинхронизировалась бы с файлами.
  Дашборд по тысячам сессий, если понадобится, строится ПРОИЗВОДНЫМ кэшем,
  пересобираемым из каталогов, — но не источником правды.
- **Проверено:** 234 теста, из них `nothing_to_do_is_done_and_never_loops`,
  `a_new_recipe_means_redo`, `a_failure_is_retried`, `a_broken_log_does_not_wedge_processing`
  и `discovery_uses_the_processing_log_not_guesswork` — про этот самый цикл.
- **Сюжет:** правильный вопрос был не «как не зациклиться», а «почему статус
  вообще приходится угадывать». Угадывать перестали.

### WP-C34 — Язык записи: выбор человека, а не догадка кода
- **Задача (владелец):** «Надо дать возможность выставить явно язык, по дефолту
  пусть определяется сам. Если пользователь поменяет — надо сбросить всю
  производную инфу, и заново сварить».
- **Решение — язык как ЧАСТЬ РЕЦЕПТА.** Он входит в метку версии транскрипта
  (`ru` → историческая `gigaam-int8`, иначе `asr-<язык>`) и в рецепт
  LLM-артефактов (`{вид}/{стиль}/{модель}/p1`, где стиль = явный шаблон или язык).
  Поэтому «сбросить производное и переварить» **не потребовало ни строчки кода**:
  рецепт разошёлся → сессия сварена по-старому → её переварит тот же механизм
  миграции архива, что чинит смену модели или окон. Сброс — по построению.
- **Почему авто НЕ выбирает ASR-модель.** Язык определяется по тексту, а текст
  выдаёт модель — которую ещё надо выбрать. Курица и яйцо. Хуже: английскую речь
  русская модель не «не распознает», а выдаст правдоподобную русскую кашу, и
  любой детектор честно скажет «это русский». Поэтому автоопределение (whatlang +
  isolang, порог 20 слов, требуется `is_reliable`) работает там, где текст уже
  есть: выбор шаблонов и языка ответа LLM. Чтобы РАСПОЗНАТЬ другой язык, его надо
  назвать. Нет модели для языка — падаем громко, а не варим русской молча.
- **Сделано:** `core/lang.rs`; `--lang` у `localvox-process`; `LOCALVOX_LANG`;
  селектор языка в вебе (`POST /api/sessions/{n}/lang`); английские шаблоны
  (summary/cleanup/note); английские числительные и имена в лексиконе.

### WP-C35 — Три дыры, которые открыл язык (нашли до приёмки)
1. **Вечный цикл: у английской сессии свой рецепт варки.** `needs_cook` спрашивала
   «сварено ли РУССКИМ рецептом» — у английской сессии ответ всегда «нет», и её
   ставили бы в очередь бесконечно. Теперь сверяемся с рецептом СЕССИИ.
2. **Вечный цикл: демон и его дочерний процесс считали рецепт по-разному.** Демон
   брал шаблон из `LOCALVOX_LLM_SUMMARY_TEMPLATE`, а `localvox-process` эту
   переменную не читал вовсе — запускается-то он без флага. Рецепты расходились,
   и протокол делался бы вечно. Привязал флаг к той же переменной; пустое значение
   («не задано») теперь трактует единственная общая функция `processing::llm_style`,
   а не каждая сторона по-своему.
3. **Проверка обоснованности разваливалась на английском — В ОБЕ СТОРОНЫ.**
   Правило «латиница ⇒ проверять» на самом деле означало «ЧУЖОЙ для записи
   алфавит ⇒ проверять», и держалось только на том, что запись русская.
   На английской записи под него попадало КАЖДОЕ слово: честный протокол получил
   шесть обвинений в выдумке («deployment», «documentation», «schedule»…), у
   такого же русского — ноль. А щедрый бюджет похожести (он задуман для
   транслита) делал проверку слепой в обратную сторону: «Thursday» обосновывался
   об «Tuesday» — модель перенесла бы встречу, а мы бы заверили.
   Переформулировал всё относительно алфавита ЗАПИСИ (`script_of` по речи).
- **Сюжет:** язык не «добавили» — он проявил, что три правила молча опирались на
  «запись всегда русская». Ни одно из них об этом не говорило.

### WP-C36 — Разбор ревью языка: 13 подтверждённых дефектов, 11 закрыто
Ревью (4 независимые линзы + опровергающая проверка каждой находки) нашло 13
подтверждённых дефектов. Из них **только 5 — про язык**; остальные 8 лежали в
коде давно, и язык их просто ПРОЯВИЛ. Закрыто:

1. **Один клик в UI уничтожал протокол.** Селектор предлагал английский всегда,
   модели для него нет: `set_lang` стирал производное → варка падала → артефакты
   не возвращались, а человеку сказали «ок». Теперь: наличие модели проверяется
   ДО разрушения; `GET /api/langs` отдаёт только языки, для которых модель есть,
   и селектор строится из него. Предлагать язык, которым не умеем, — обещать
   невыполнимое.
2. **`LOCALVOX_LANG` действовал задним числом на ВЕСЬ архив.** Язык в рецепте +
   чтение переменной для старых сессий = «весь русский архив сварен не так» →
   переварка английской моделью, `best` уезжает на кашу, обратно не чинится.
   Теперь язык ФИКСИРУЕТСЯ в meta при создании сессии; переменная влияет только
   на новые записи.
3. **Движок затирал выбранный язык.** Мета держится в памяти (там `lang: None`) и
   пишется целиком → выбор человека исчезал на ближайшей ротации чанка. Теперь
   `save_meta` сливается с файлом; `finalize_all` дописывает ДО снятия маркера;
   `--lang` на живой сессии отказывает.
4. **Пропуск варки не возвращал `best`.** Сварили en → best на en → вернули ru →
   рецепт совпал → варка пропущена → best НАВСЕГДА на чужой каше, и протокол
   строился из неё. Теперь пропуск чинит `best`.
5. **Кнопка «♻ Переварить» стирала протокол и не пересоздавала его** (СТАРЫЙ баг):
   у демона флаги включены по умолчанию, у API — выключены; джоба ставилась без
   `--summary`. Плюс `recook` не чистил журнал — тот утверждал «сделано» про
   удалённый файл. Теперь флаги читаются из ОДНОГО места
   (`jobs::post_processing_from_env`), журнал чистится, работа ставится в очередь
   ДО разрушения.
6. **Вечный цикл: retention съел аудио** (СТАРЫЙ баг). Транскрипт жив → discovery
   требует протокол → варка возвращает Empty → `continue` → журнал не пишется →
   через 5 с всё сначала, вечно. Discovery решала по транскрипту, обработчик — по
   аудио. Теперь: нет аудио, но есть расшифровка → LLM работает (ей аудио и не
   нужно).
7. **Демон и его дочерний процесс считали рецепт по-разному** — вечный цикл.
8. **Английские числа ≥ 100** ломали проверку: «two hundred» → [2, 100], любой
   протокол в карантин. Введены множители разряда. Плюс: **запись** разбираем

### WP-C37 — Списки имён выброшены. Людей размечает NER-модель, а не словарь
- **Претензия владельца (в точку):** «убрать жёсткие завязки на ограниченные

- **Он прав, но не одинаково по всем пунктам, и это важно.** Разведка (5 областей,
  веб + проверка каждой находки) дала неожиданное уточнение:
  * **списки ИМЁН — тупик.** Имён в языке бесконечно много, а главное — список не
    видит контекста и потому НЕ СНИМАЕТ ОМОНИМИЮ НИКОГДА;
  * **таблицы ЧИСЛИТЕЛЬНЫХ — не тупик.** Числа и даты это закрытый класс с
    конечной грамматикой; правила бьют тут любую модель по полноте и дают
    стопроцентную объяснимость. Их надо сделать МОДУЛЬНЫМИ, а не заменить моделью.
- **Решение — GLiNER (`gliner_multi-v2.1`, Apache-2.0), ONNX через уже подключённый
  `ort`.** Энкодер-классификатор: скорит СПАНЫ ВХОДА, декодера у него нет — выдумать
  имя физически не может. Типы сущностей задаются СТРОКАМИ («человек»), поэтому в
  коде не осталось ни одного имени и ни одного языка.

**ЗАМЕРЕНО НА ЖИВОЙ МОДЕЛИ (не предположено):**

| фраза | int8 | q4f16 | fp16 |
|---|---|---|---|
| «**Роман** закроет задачу» → человек | 0.22 | 0.67 | **0.89** |
| «дописать **роман**» → человек | 0.03 | — | **не найден** |
| «**Marcus** will ship it» → человек | 0.17 | 0.88 | **0.97** |

- **Омонимия снята контекстом.** Ровно то, чего требовал владелец и чего словарь
  не мог дать никогда.
- **int8 НЕ БРАТЬ.** У mDeBERTa он разваливает калибровку: сигнал есть, но скоры
  падают вчетверо, и при любом разумном пороге модель молча не находит НИЧЕГО —
  это неотличимо от честной пустой записи. Худший вид поломки. Выбор файла в коде
  идёт по предпочтению (fp16 → q4f16 → fp32), на int8 — громкое предупреждение.

**Что судит модель — ТОЛЬКО ЛЮДЕЙ, и это тоже замер, а не вкус.** Сначала отдал ей
даты и суммы — получил ложные обвинения: «около двухсот тысяч» → «порядка 200 000»
это ЗАКОННЫЙ ПЕРЕСКАЗ, а проверка слов объявляла выдумкой «порядка», «following»,
«suite». Имя пересказать нельзя — оно либо звучало, либо выдумано. Срок и сумма —
это ЧИСЛО, а числа проверяются детерминированно.

**Попутно найдены два молчавших бага:**
1. **Стеммер разводил имя с его же падежом:** Snowball даёт «иван» → «ива», но

   «спикера». Слов для роли бесконечно много — это та же ошибка, что список имён.

   **Решение: дать модели ВТОРУЮ метку — «говорящий или роль», и спрашивать ДВУМЯ
   НЕЗАВИСИМЫМИ проходами.** Правило: имя обязано ПЕРЕВЕСИТЬ роль на том же спане.
   ```
   Говорящий   имя 0.53 < роль 0.79  → роль        Роман   имя 0.54 > роль 0.49 → ИМЯ
   Рассказчик  имя 0.55 < роль 0.62  → роль        Marcus  имя 0.88 > роль 0.77 → ИМЯ
   Спикер          —      роль 0.59  → роль        Иван    имя 0.85 > роль 0.78 → ИМЯ
   ```
   **Две метки в ОДНОМ проходе не годятся — они отбирают вес друг у друга**: с парой
   меток «Роман закроет задачу» перестал быть человеком, а омонимия ради этого и
   затевалась. Абсолютный порог для роли тоже не годится: она срабатывает и на
   именах (Иван — 0.78). Значение имеет только ПОРЯДОК.

3. **Пустые разделы вернулись** (см. WP-C40): промптом не лечатся.

**Проверено на живом архиве:** сессия, уехавшая в карантин, теперь даёт чистый
`summary.md`. Корпус 18/18, тесты 273/273.

- **Сюжет:** корпус окупился в первый же прогон. Шесть придуманных фраз показывали
  6/6 — и скрывали три дефекта, каждый из которых бил по живому архиву.

### WP-C43 — «Протокол» переименован в «Сводку», читаемый текст поднят выше
- **Владелец:** «читаемый текст должен быть до протокола. И протокол — дерьмовое
  название, summary или как-то ещё универсально — лучше».
- **Он прав по сути, а не по вкусу.** «Протокол» бывает у ВСТРЕЧИ. А запись бывает
  лекцией, видео, звонком, мыслью вслух — и файл при этом ОДИН И ТОТ ЖЕ
  (`summary.md`). Название врало о содержимом и навязывало читателю чужую рамку —
  ту самую, из-за которой у лекции когда-то появились «Решения» и «Поручения».
- **Стало «Сводка»** — по-русски, универсально, и совпадает с тем, чем артефакт
  является на самом деле. Переименовано везде, где слово видит человек: вкладка,
  карточка сессии, черновик, подтверждения переварки и смены языка, справка CLI,
  описания MCP-инструментов. На странице упоминаний «протокол» — ноль.
- **Порядок вкладок:** Расшифровка → **Читаемый текст** → Сводка → Версии.
  Читаемый текст ближе к записи, чем сводка: сводка это уже ВЫВОД из него. Читать
  надо в том порядке, в котором вещи производны друг от друга.

### WP-C44 — Аудио выбрасывалось молча. Худший баг за проект
- **Владелец:** «скорость воспроизведения раза в 2 увеличена, и артефакты на фоне.
  Судя по дерьмовому качеству текста, он транскрибировался с вот такой x2 записи».
- **Он был прав по симптому и прав по диагнозу.** Замерил по живому архиву —
  сколько аудио на источник против реального времени:

| сессия | по часам | микрофон | системный звук |
|---|---|---|---|
| **120809** (та, где текст — каша) | 164.8 c | **90.2 c (0.55)** | **83.5 c (0.51)** |
| 195504 | 175.8 c | 175.7 c (1.00) | 116.7 c (0.66) |
| 202009 | 219.5 c | 219.4 c (1.00) | 164.5 c (0.75) |

  **Записывалась половина времени.** Поэтому файл играл вдвое быстрее, на склейках
  щёлкал, а ASR кормили сжатой во времени кашей.

**ПРИЧИНА №1 — молчаливая потеря записи.**
```rust
match tx2.try_send(PcmChunk { … }) {
    Ok(()) => {}
    Err(TrySendError::Full(_)) | Err(TrySendError::Disconnected(_)) => {}  // ← в мусор
}
```
Канал `bounded(1024)` = **33 секунды буфера на оба источника**. Потребитель — ОДИН
поток: пишет на диск с fsync, гоняет VAD, режет сегменты. Когда рядом молотит варка
(ONNX + Ollama съедают ядра), он голодает, очередь забивается — **и аудио летит в
мусор. Без единой строчки в логе.**

**Выбрасывалось единственное, что невосстановимо.** Расшифровку, сводку, индексы —
всё можно пересоздать ИЗ АУДИО. Аудио нельзя пересоздать ни из чего. Это прямо
нарушало принцип, записанный в собственных комментариях к `jobs.rs`:
«Неприкосновенно только само аудио».

**Починка:** канал БЕЗГРАНИЧНЫЙ, `send` вместо `try_send`. Давление оплачивается
ПАМЯТЬЮ, а не потерей: 32 КБ/с на источник, минутный затык — 2 МБ. Плюс **сторож
очереди**: молчать о затыке тоже нельзя — растущая очередь значит, что запись
отстаёт, и об этом теперь говорится вслух (лог + статус в TUI).

**ПРИЧИНА №2 — самодельный ресемплер («артефакты на фоне»).**
Микрофон 48 кГц → 16 кГц делался **линейной интерполяцией БЕЗ ФИЛЬТРА**:
- **алиасинг**: тон 12 кГц не исчезает, а ЗАВОРАЧИВАЕТСЯ в 4 кГц — прямо поверх
  голоса. Это портило и слух, и ASR: модель слышала то, чего не было;
- **разрывы**: каждый колбэк начинал интерполяцию с нулевой позиции — щелчки на
  каждом стыке буферов.

Заменено на `rubato` (FFT-ресемплер с фильтром и памятью между блоками). Три теста
доказывают: тон выше Найквиста ГАСИТСЯ (а не заворачивается), голос 1 кГц проходит,
длительность сохраняется один к одному.

Системный звук был в порядке — там ресемплит сама WASAPI (`autoconvert: true`).

- **Сюжет:** этот баг не поймал бы ни один юнит-тест — он проявляется только под
  нагрузкой, на живой машине, и молчит. Его нашёл ВЛАДЕЛЕЦ, ушами. Единственная
  причина, по которой мы вообще смогли его подтвердить, — что аудио и meta лежат
  рядом и их можно сверить с часами. Хранить сырьё и метаданные — окупается.

### WP-C45 — Сторож целостности записи + закрытие фаз A–C
- **Сторож целостности.** Потерю аудио мы устранили (WP-C44), но устройство может
  отвалиться и без нас. Теперь запись СЧИТАЕТ САМА СЕБЯ: сколько аудио пришло
  против реального времени. Расхождение больше 5 % — громкая ошибка в лог, а не
  «догадайся ушами через две недели», как вышло у владельца.
  Пауза считается ЧЕСТНО: часы стоят вместе с записью, иначе сторож кричал бы на
  каждую паузу и его перестали бы слушать. Три теста: здоровая запись молчит,
  потеря половины кричит, пауза за потерю не принимается.
- **План фаз A–C закрыт.** Из открытого осталось только осознанно отложенное:
  * **пословные таймкоды из CTC — ОТМЕНЕНО**, и это замер, а не лень: CTC ставит
    токены неточно, фраза разъезжалась на 13 секунд. Строка = ОКНО, границы в
    сэмплах, плеер играет ровно написанное — по построению;
  * `llm.toml` и `meta.sqlite` — потребителя нет, флаги/env закрывают задачу.
- **Шаблоны стартового набора дописаны:** `standup-ru` (разбор ПО ГОВОРЯЩИМ, а не
  по темам; пункт, о котором не сказали, не печатается вовсе) и `one-on-one-ru`
  (там говорят о ЛЮДЯХ, и выдуманная деталь — не ошибка, а сплетня, сгенерированная
  машиной; личное передаётся СЛОВАМИ ЧЕЛОВЕКА, без интерпретаций и диагнозов).

## WP-C46 — Диаризация: КТО говорит (модель-независимая часть)

**Проблема.** Строка транскрипта подписана ИСТОЧНИКОМ ЗВУКА: `[Я]` — микрофон,
`[Собеседники]` — системный звук. На созвоне вчетвером трое собеседников приходят
одним смешанным потоком и становятся одним безликим «Собеседники». Из-за этого
сводка не может честно написать «Иван взял миграцию»: мы не знаем, что это сказал
Иван, — а гадать нельзя. Это тот же запрет, что и в NER: **имя, которого не было в
звуке, появиться не должно ни при каких условиях.**

**Устройство** (ни один шаг не генерирует текст — это классификаторы над входом,
как и GLiNER; выдумать человека они физически не могут):

1. **сегментация** — модель размечает по кадрам, кто говорит, включая ПЕРЕКРЫТИЕ
   речи (двое разом);
2. **эмбеддинги** — на каждый отрезок ЧИСТОЙ речи считается вектор ГОЛОСА (тембр,
   а не слова: языко-независим по природе);
3. **кластеризация** — векторы сливаются в людей. Числа спикеров мы НЕ ЗНАЕМ и
   спрашивать его у человека нельзя: он тоже не считал;
4. **лента** — «с 12.4 по 18.9 говорит участник 2»; по ней подписываются строки;
5. **профили** — человек однажды назвал имя, и голос узнаётся в следующих сессиях.

**Исследование (workflow, 5 линз) дало два решения, оба против «взять готовое»:**

- **sherpa — отвергнут, и это про линковку, а не про вкус.** `sherpa-onnx-sys`
  объявляет `links = "sherpa-onnx"`, а `ort-sys` — `links = "onnxruntime"`. Cargo
  конфликта НЕ УВИДИТ и соберёт — упадёт линкер: две статические копии ONNX
  Runtime в одном exe (LNK2005), плюс `/MT` против `/MD` (LNK2038). Обход через
  общий `onnxruntime.dll` обрезал бы opset для GigaAM и GLiNER. Пишем своё на том
  же `ort`, который уже несём.
- **Модель сегментации — `onnx-community/pyannote-segmentation-3.0`**: MIT (CNRS),
  **не gated** (gate у оригинала — маркетинговая форма, а не лицензия), 5.7 МБ.
  Порядок 7 классов powerset подтверждён ДВУМЯ независимыми источниками (config.json
  реэкспорта и C++ `InitPowersetMapping()` в sherpa). Выход графа — **log-softmax**,
  хотя тензор зовётся `logits`: имя врёт, проверено запуском.
  **Квантизация не берётся:** int8 расходится с fp32 на 7 % кадров, размазывает
  границу реплики с 3.5 с до 6.6 с и ВЫДУМЫВАЕТ перекрытие речи; fp16 на CPU падает
  с segfault. Экономия — 4 МБ. Ровно тот же ожог, что с int8-mDeBERTa, только
  измеренный ЗАРАНЕЕ.
- **Sortformer (NVIDIA) отвергнут по сути, а не по лицензии:** у него нет
  эмбеддингов, а значит «это снова Иван» между сессиями невозможно в принципе.
  **3D-Speaker — ловушка:** их красивая колонка «DER с overlap-detection» получена
  ВЫЗОВОМ pyannote (`infer_diarization.py:125`), своей модели сегментации у них нет.
  README снова соврал; спасла проверка по коду.

**Что сделано и доказано (30 тестов, ни одного файла весов на диске):**
- `cluster.rs` — агломеративная кластеризация, косинус, **average-linkage** (single
  склеивает двух людей цепочкой через один пограничный отрезок);
- `timeline.rs` — кадры → лента. Кадры ПЕРЕКРЫТИЯ выброшены из эмбеддингов: смесь
  двух голосов даёт вектор несуществующего человека. Вдох посередине реплики её не
  заканчивает. Строку, поделённую двумя поровну, НЕ подписываем никем: приписать её
  одному значит вложить в его уста чужие слова;
- `mod.rs` — потоковый `Runner` (час звука в f32 — это 230 МБ, и держать его в
  памяти незачем: кадры и векторы считаются внутри 10-секундного окна). Сегментация
  и эмбеддер — ТРЕЙТЫ, поэтому весь конвейер доказывается поддельными моделями;
- **сведение дорожек**: голос собеседника слышен и в колонках, и в микрофоне (эхо).
  Диаризованные порознь, дорожки дали бы одного человека, разрезанного надвое.
  Центроиды кластеризуются ещё раз, вместе. **«Я» — не «кто больше наговорил в
  микрофон»** (так им становилось эхо на ничьей), а **тот, чей голос НЕ ВОЗВРАЩАЕТСЯ
  из колонок**: звонок его не транслирует;
- `profiles.rs` — имя даёт ЧЕЛОВЕК, порог узнавания строгий (0.70): не узнать дёшево
  (назовёт ещё раз), узнать не того — клевета. Биометрия стирается одной кнопкой;
- `roster.rs` — состав записи с голосами. Благодаря ему «Участник 2 — это Иван»
  стоит правку строчки, а не повторный прогон моделей по звуку;
- `versions.rs::relabel_speaker` — имя меняется во ВСЕХ версиях сразу (иначе человек
  остался бы «Иваном» в сырой расшифровке и «Участником 2» в причёсанной — двумя
  разными людьми в одной записи). **Аудио не переваривается: оно не изменилось.**
- **Тест поймал настоящую ошибку:** два участника ОДНОЙ записи получали одно имя
  (порог узнавания — не тождество). Имя достаётся самому похожему, остальным — номера.
- **Рецепт.** Разметка говорящих входит в `cook_recipe` (транскрипт с именами и без
  — разные транскрипты, из них выходят разные сводки), поэтому архив доразметится
  сам, тем же механизмом миграции, что и при смене языка. Решение «размечаем ли» —
  в ОДНОМ месте (`diarize::enabled()`), и демон, и варка спрашивают там: расхождение
  рецептов между процессами уже ДВАЖДЫ подвешивало очередь навсегда.

### Модель голоса — выбрана ЗАМЕРОМ, а не по README

**ERes2Net base 200k** (3D-Speaker, Apache-2.0, качается анонимно с релизов k2-fsa),
40 МБ, вход `x [N,T,80]` (kaldi-fbank), выход `embedding [N,512]`. Замер на РУССКОЙ
речи (bench/golos-crowd), отрезки 1.5 c: EER 5.1 %, свой-свой 0.62 против
свой-чужой 0.20.

Отвергнуты по числам, а не по репутации:
- **wespeaker CAM++ — EER 18–39 %**, то есть он почти не отличает людей. Именно его
  берёт `pyannote-rs`, откуда мы копировали форму графа. Слепое доверие обошлось бы
  дорого.
- **3dspeaker campplus_en_voxceleb — EER 32.9 %.**
- **int8** у эмбеддера: на CAM++ косинус fp32↔int8 падал до **0.391** — косинусная
  геометрия, то самое, чем мы отличаем людей, разъезжается первой. Урон зависит от
  архитектуры (ERes2Net терпит, CAM++ — нет), и проверять это надо каждый раз.
- **fp16 вообще не грузится** (Type Error на CPU) — на обеих моделях.

**Пороги пересчитаны.** `RECOGNISE_AT` стоял на 0.70 «с запасом» — и это оказалось
МИМО: у этой модели «свой-свой» в среднем 0.62, и порог 0.70 не принял бы почти ни
одного верного совпадения. Строгость, которая не узнаёт никого, — не строгость, а
сломанная функция. Теперь 0.60 (правый край «0.1 % ложных срабатываний»).

### Фичи: свой kaldi-fbank, сверенный с эталоном

Крейт `kaldi-native-fbank` 0.1.0 БРАТЬ НЕЛЬЗЯ: у него пол логарифма 1e-20 вместо
`FLT_EPSILON`, и это молча портит ТИХИЕ кадры, а CMN потом размазывает ошибку по

## WP-C47 — Вопрос к архиву (F4, последний этап): «что решили по миграции?»

**Проблема.** Поиск отвечает СТРОЧКАМИ, а человек спрашивает вопросами. Реестр
фич закрывал F4 тремя этапами (full-text → embeddings → RAG-чат); первые два были
сделаны, третий — нет.

**Это не «чат с моделью», и разница принципиальная.** Модель, которую спросили «что
решили по миграции», ответит ВСЕГДА: она знает, что бывает на таких встречах, и
соберёт правдоподобный ответ из воздуха. Человек примет его за факт и построит на
нём решение — это худшее, что продукт может сделать. Поэтому:

1. **Сперва поиск** (гибридный: слова + смысл). Ничего не нашлось — **модель не
   вызывается ВООБЩЕ**. «В записях этого нет» выдаёт код, а не промпт: промпт — это
   просьба, а не механизм (правило, оплаченное дважды).
2. **Фрагменты, а не сниппеты.** Сниппет в 200 знаков — это подсветка, по ней можно
   только угадать. Каждый хит разворачивается в НАСТОЯЩИЙ кусок разговора: соседние
   реплики вокруг найденной, с говорящим (диаризация!) и таймкодом.
3. **Ссылки обязательны.** Фрагменты пронумерованы, модель ссылается на номера,
   ответ отдаёт наружу ТЕ САМЫЕ куски — с сессией и временем, чтобы открыть и
   послушать. Номер, которого модели не давали, ссылкой не считается: это выдумка.
4. **Ответ проверяется** той же машинкой, что и протокол (числа и имена).

**Подстановка в шаблон — за ОДИН проход.** Расшифровка может сама содержать
`{{fragments}}` (человек произнёс, ASR записал), и второй проход подставил бы в неё.
Это не паранойя, а инъекция промпта через микрофон.

**ЖИВОЙ ЗАМЕР — и честная граница проверки.** Спросил архив про рецепт. Ответ
построен по записям, со ссылками, `verified=true`, необоснованных чисел и имён нет.
Но модель добавила **«хабанеро», которого в записях НЕТ** (она знает рецепты). Слово
нарицательное, русское, строчное — ни числом, ни именем не является, и
детерминированная проверка его пропустила.

Ужесточить её («любое слово, которого нет в источнике») НЕЛЬЗЯ: модель законно
перефразирует, и такая проверка кричала бы на каждый честный ответ. Предупреждение,
которое кричит всегда, читать перестают — этот урок уже оплачен ложными тревогами на
ролях в NER. Поэтому механизм другой и он в UI: **под ответом всегда лежат источники
с таймкодами**. Ответ, который не на что открыть и послушать, доверия не заслуживает,
и продукт говорит это прямым текстом.

## WP-C48 — «Не понял, что он тут нашёл»: поиск объясняет себя

**Жалоба владельца (13.07.2026):** «в большинстве результатов я не понял, что он там
нашёл похожего на запрос». Справедливо. Три РАЗНЫЕ причины, и все три — настоящие.

**1. Сниппет показывал не то место.** Индекс ищет со СТЕММИНГОМ («миграции» по
запросу «миграция»), а сниппет искал слово БУКВАЛЬНО. Не находил — и показывал
НАЧАЛО ТЕКСТА. Человек видел строчку, в которой нет ни одного слова запроса.
Теперь сниппет режется тем же анализатором, каким текст попал в индекс, и всегда
показывает найденное место.

**2. Совпадения на стоп-словах.** Поиск честно находил записи по «и», «на», «что» —
совпадение формально есть, а смысла в нём нет. Поиск, который находит запись по
союзу «и», не находит НИЧЕГО. Выброшены стоп-слова (русские и английские — архив
двуязычный, «the» такой же шум). Фильтр стоит ДО стеммера: список состоит из
словоформ, после стемминга это уже другие слова.

Индекс от правки анализатора не пересобирался бы сам: файлы сессий не менялись,
индекс «свежий». Та же болезнь, что у рецепта варки, и лечится так же — **ревизией
анализатора** (`INDEX_REV`): сменилась — индекс пересобран.

**3. Семантический хит вообще не обязан содержать слова запроса** — и это не баг, а
его суть. Но человеку об этом никто не говорил. Теперь каждый результат несёт:
* **подсветку** совпавших слов (с морфологией: «курица» → подсвечено «курицу»);
* **«почему нашлось»**: `слова` | `смысл` | `слова + смысл` (пришёл из обоих
  каналов — самый надёжный);
* честное **«без совпадений по словам»** там, где их нет.

Подсветка вставляется ПОСЛЕ экранирования: расшифровка, в которой человек произнёс
«меньше скрипт больше», не должна вносить в страницу разметку.

**Попутно — два бага, которых никто не искал:**
* **Гибрид падал целиком, если лексический канал отказал.** Семантика деградировала
  мягко, лексика — нет. Теперь симметрично: жив хотя бы один канал — поиск работает.
* **Строка поиска — не язык запросов.** Разборщик tantivy считает `-`, `"`, `:`
  синтаксисом и целые обычные фразы отвергал совсем («Only excluding terms given»),
  а поиск отвечал на это ОШИБКОЙ — то есть отказывался искать. Теперь: сперва
  пробуем как синтаксис (кто владеет — пользуется), не вышло — ищем как слова.

## WP-C49 — Лог варки: 1125 строк чужой отладки → 7 строк по делу

**Жалоба владельца:** в логе демона появились строки вида
`\x1b[2m…\x1b[0m \x1b[32m INFO\x1b[0m Allocated memory at 000001D02624C080…` —
«странные байты» и внутренности чужого аллокатора.

**Это была моя регрессия, и это надо назвать вслух.** В `localvox-process` не было
подписчика логов вообще (WP-C46: из-за этого молчали ВСЕ наши предупреждения). Я его
добавил — и вместе с нашими сообщениями наружу полезло то, чему раньше просто некуда
было писать.

**Причина 1 — ONNX Runtime.** Крейт `ort` создаёт окружение ORT с уровнем VERBOSE и
перекладывает фильтрацию на `tracing`, то есть на нас. Не отфильтруешь — и на каждый
инференс в лог сыплется бухгалтерия аллокатора и списка графовых трансформеров.

**Ловушка, на которой первая попытка починки провалилась:** я положил `ort=warn` в
ДЕФОЛТ фильтра. А в `.env` стоит `RUST_LOG=info` — он перекрывает дефолт ЦЕЛИКОМ, и
шум вернулся. Молчание чужих библиотек навешивается **поверх** любого `RUST_LOG`, а
не вместо него. Вернуть отладку можно, назвав библиотеку явно (`RUST_LOG=info,ort=info`)
— молчание не должно превращаться в невозможность посмотреть. Правило доказано тестом,
а не проверено глазами по логу.

**Причина 2 — ANSI.** Цвет писался безусловно, а вывод дочерней варки перехватывает
демон и переливает в свой лог. В файл попадали сырые управляющие последовательности
вместо времени. Теперь цвет — только если stderr действительно терминал.

Оба решения — в ОДНОМ месте (`core::cli::init_tracing_tool`), которым пользуются все
бинари: решать это порознь в каждом значит однажды снова залить лог.

**Замер:** тот же прогон варки — было **1125 строк** (868 из них — ORT, 1121 с
ANSI-байтами), стало **7 строк**, все наши.

## WP-C50 — Три правки по итогам живой работы

### 1. Новая сессия появляется в архиве СРАЗУ

**Жалоба:** «когда завершаешь принудительно сессию, надо сразу создавать запись в
сессиях, а потом уже наполнять её текстом, а то непонятно, где эта новая сессия».

Причина: «идёт запись» определялось ТОЛЬКО по свежести файлов в `audio/`. Движок

прячет. Человек не понимал, КУДА ТЕПЕРЬ ПИШЕТСЯ звук.

Починено с двух сторон: `meta.json` пишется сразу при рождении сессии (а не когда
закроется первый чанк), и свежая мета — такое же свидетельство жизни, как свежий
аудио-файл. Защита от «вечно идёт запись» после падения демона сохранена: через две
минуты без единого обновления сессия перестаёт считаться живой.

Клип-эндпоинт умел играть ОДНУ дорожку и не длиннее 120 с — этого хватало «послушать
реплику», но не «послушать запись». Теперь без параметра `source` он отдаёт **смесь
обеих дорожек**: слушать половину диалога бессмысленно. Сложение — с защитой от
клиппинга (сумма двух громких сэмплов вылезает за i16 и заворачивается в
противоположный знак: это не «чуть громче», это треск вместо речи).

Плеер берёт запись **окнами по 10 минут**, а не одним куском: час записи — это 115 МБ
в памяти сервера и браузера, и собирать их ради «мало ли послушаю» нечестно по
отношению к машине. Окно кончилось — подхватывается следующее.

### 3. Детект встреч: у автомата нет и не будет надёжного признака

**Честный ответ на вопрос «как детектировать сессии».** Автодетект (`detect.rs`)
видит звонок по тому, что приложение ДЕРЖИТ МИКРОФОН, — и для Zoom, Teams, браузера
это работает. **Очную планёрку за столом он не увидит никогда:** с точки зрения
системы это тот же фоновый шум, что и весь день. Надёжного автоматического признака
встречи в комнате не существует, и притворяться, что он есть, — значит врать.

Поэтому у человека теперь есть кнопка **«🎙 Новая встреча»**: текущая запись
закрывается (уходит в варку), новая рождается ВСТРЕЧЕЙ — с названием, которое видно
и в списке, и в имени каталога. Кириллица транслитерируется («Планёрка» →
`20260713_181500_planerka`), иначе название просто пропадало бы из имени папки.

В мете появились `title` и `meeting`; признак встречи ставит либо человек, либо
детектор звонка — оба одинаково настоящие.

**Дальше по этой линии:** голосовая команда («запиши встречу») — она дёргает тот же
маркер, что и кнопка; и календарь — название, участники и границы события. Оба
опираются на уже сделанное: маркер `.start_meeting` и `meta.title`.

## WP-C51 — Костыли вон: состояние сессии, лог, плеер, голос

### 1. «Пусто» и «не обработано» — РАЗНЫЕ вещи

**Жалоба владельца:** «Мёртвая и пустая — не равно необработанная, необработанные
пусть висят, хорош костылить тут. 2 минуты без обновлений, ещё что-то. А если я
страницу обновлю?»

Справедливо, и костыль был мой. Список прятал всё, где в расшифровке ноль строк, —
а необработанная сессия это тоже ноль строк. Человек не находил свою запись и решал,
что она пропала. Прятать теперь можно ТОЛЬКО обработанное-и-пустое: там правда речи
не нашлось.

Второй костыль — «идёт запись» определялось по свежести файлов (моложе двух минут).
Выброшено. Спрашиваем прямо: **держит ли кто-нибудь лок рабочего каталога.** Лок
берёт движок на всё время работы; свободен — движка нет, маркер устарел. Это не
эвристика, а факт операционной системы, и он не зависит ни от таймеров, ни от того,
обновил ли человек страницу.

Состояния теперь называются своими именами: `● идёт запись`, `⚙ обрабатывается`,
`⏳ в очереди`, `⚠ обработка сорвалась`, `не обработана`, `речь не распознана`.
Занятость — жёлтым: это «мы этим заняты, подожди», а не ошибка.

### 2. Лог: вторая линия обороны

Фильтр у источника (`localvox-process`) стоял правильно — но у владельца крутился
СТАРЫЙ релизный бинарь: пересобрать его не вышло, файл держал его же работающий
демон, и я этого не заметил. Виноват.

Чинить надо было не только это. Лог демона читает ЧЕЛОВЕК, и заливать его чужой
бухгалтерией памяти может любая соседняя версия бинаря или библиотека, которую мы
подключим завтра. **Свой лог мы защищаем сами:** демон, переливая вывод дочернего
процесса, снимает ANSI-последовательности и выбрасывает внутренности ONNX Runtime
(BFCArena, «Allocated memory at…», GraphTransformer). Наши строки не трогает.

### 3. Плеер: пустой `<audio>` — это и есть «серое пространство»

Тег `<audio controls>` без источника браузер рисует серым прямоугольником, который
ничего не делает и выглядит поломкой. Теперь плеер показывается ТОЛЬКО когда аудио
загружено; до этого — «загружаю аудио…», а если не вышло — прямая причина.

### 4. Голосом: «начни встречу»

Кнопка требует свободных рук и открытого браузера, а встреча начинается, когда
человек уже сел за стол и говорит. Фразы: «начни встречу», «новая встреча», «запиши
встречу» (настраивается `LOCALVOX_LIGHT_VOICE_MEETING`). Всё, что сказано после
фразы, — название.

**Ловушка, пойманная тестом:** «запиши встречу» начинается с активатора ЗАМЕТОК
(«запиши»). Не разбери мы встречу первой — человек попросил бы пометить встречу, а
получил бы запись в блокнот текстом «встречу», и понял бы это через час. Встреча
разбирается ДО заметок.

Голос и кнопка дёргают ОДИН и тот же маркер `.start_meeting` — двух разных путей
«начать встречу» в системе нет.

## WP-C52 — Лог: лечим причину, а не симптом. И ложный сторож

### 1. Чужие логи: чёрный список выброшен

Владелец: «может мы уже закончим срать в лог? … придумай, что можно сделать без
больших костылей, лучше вообще без костылей». Справедливо: я фильтровал строки ORT
по подстрокам (`BFCArena`, `Allocated memory`) — это чёрный список, он навсегда
отстанет от следующей библиотеки.

**Причина.** Крейт `ort` создаёт окружение ONNX Runtime с уровнем VERBOSE и
перекладывает фильтрацию на `tracing`, то есть на нас. Строки уже порождены, прошли
FFI, отформатированы — и только потом выброшены. Лечение симптома.

**Решение — три механизма, ни одного костыля:**
1. **`ort::Environment::set_log_level(Warning)`** (`core::onnx`): ONNX Runtime молчит
   у СЕБЯ. Строки не рождаются вовсе. `LOCALVOX_ONNX_LOG=info` возвращает всё
   обратно — молчание не должно превращаться в невозможность посмотреть.
2. **stdout = бизнес, stderr = диагностика.** Дочерний процесс печатает РЕЗУЛЬТАТ в
   stdout, а диагностику (свою и чужих библиотек внутри себя) — в stderr. Демон
   льёт stdout в лог на INFO, stderr — в debug и в «хвост» для объяснения падения.
   Чужая библиотека физически не может засорить лог: она пишет не в тот поток.
3. Уровни логов остаются управляемыми через `RUST_LOG` (молчание навешивается
   ПОВЕРХ, а не вместо: `RUST_LOG=info` в `.env` иначе перекрывал бы дефолт целиком
   — на этом первая попытка и провалилась).

**Замер:** 1125 строк на одну варку → 3 строки stdout + 3 строки stderr. Проверено,
что молчит именно источник: со снятым фильтром (`RUST_LOG=info,ort=info`) шума
по-прежнему НОЛЬ.

`tantivy` НЕ глушим: владелец прямо сказал, что нормальный объём чужих логов не
мешает. Шесть строк на пересборку индекса лога не загораживают, а затыкать
библиотеку, которая говорит по делу и в меру, — перегиб.

### 2. «ПОТЕРЯ ЗАПИСИ» — сторож врал

В логе на живой машине: `ПОТЕРЯ ЗАПИСИ: получено 16 c аудио за 17 c реального
времени`. Потери не было.

Сторож считал секунды **у потребителя** — после очереди. Демон поставил в очередь 17
сессий, варка забила ядра, потребитель отстал на 45 кусков — и сторож объявил
потерей аудио, которое целым лежало в памяти (канал безграничный, WP-C44).

**Предупреждение, которое врёт, опаснее молчания:** его перестают читать и пропускают
настоящую аварию. Счётчик перенесён **ко входу** — туда, где звук приходит с
устройства и ложится в канал. Потеря записи — это вопрос об УСТРОЙСТВЕ («дошёл ли
звук»); всё, что после этой черты, — наша очередь, то есть задержка, а не потеря.
Тест: `a_backlog_in_our_own_queue_is_not_a_loss`.

### 3. Под ложной тревогой была настоящая беда: варка душила запись

Очередь PCM росла не просто так — варка (ONNX + LLM) забирала все ядра, и захват
звука начинал отставать. Это не вопрос производительности, а **приоритет ценностей**:
аудио — единственное, что нельзя пересоздать. Транскрипт, сводка, индекс делаются из
него заново; он — ни из чего.

Дочерний процесс варки запускается с `BELOW_NORMAL_PRIORITY_CLASS`: фоновая работа
обязана уступать записи, а не соревноваться с ней. Не `idle` — на занятой машине
idle-процесс может не получить процессор вовсе, и архив никогда не доварится.

## WP-C53 — Код на английском: комментарии, логи, диагностика

**Решение владельца:** комментарии и логи в коде — на английском; `docs/*.md` остаются
русскими; словарь: **варка → cook** (НЕ `refine`: `refine` уже занят причёсыванием

**Объём:** 6196 строк с кириллицей в 88 файлах → 1300. Разница не в том, что часть не

- **интерфейс**: веб, TUI, трей, экспортируемые документы, тексты ошибок API (их видит

  на них проверяется морфология и грамматика;
- **HTTP-коды по тексту ошибки**: `http.rs` сопоставляет русские подстроки со статусами

перестал бы находить что-либо. Подстроки переведены синхронно с сообщениями.

откатило ВСЮ несохранённую работу дня (36 файлов). Восстановлено полностью из
уцелевшего снимка (`git checkout <stash-commit> -- .`), ничего не потеряно, ничего не
закоммичено. Урок: агентам, работающим параллельно в одном дереве, любые git-операции
надо запрещать явно — один `stash` едва не стоил дня работы.

**Итог:** 344 теста зелёные, clippy чист, релиз собран.

## WP-C54 — Поиск по смыслу выдавал уверенную чепуху. И границы фрагмента

### 1. «Капрезе»: модель была не та, и порог тут ни при чём

**Жалоба владельца:** «по поиску по смыслу — капец сколько выдаётся, всё левое,
специально сделал поиск по слову капрезе, его вроде вообще не было».

Первая догадка — «нет порога отсечения» — оказалась ВЕРНОЙ ЛИШЬ НАПОЛОВИНУ. Замер на
живом архиве (`nomic-embed-text`, 238 документов):

```
  запрос              есть в архиве?   топ-1
  «капрезе»           НЕТ              0.830
  «квартальный…»      НЕТ              0.851   ← «Мужики! Концы будете?»
  «курица»            ДА               0.765
```

**Мусор ранжируется ВЫШЕ верного попадания.** Порог тут не спасает: ставить его не на
что. Причина — сама модель: у `nomic-embed-text` косинусы на русском зажаты в узкую
полосу (медиана 0.65) и сигнала не несут. Префиксы задачи (`search_query:` /
`search_document:`, которых мы не ставили) помогают, но недостаточно: мусор
«квартальный бюджет» 0.726 против верного «курица» 0.732.

**`bge-m3`** (мультиязычная, для ретривала; в `local-models.md` она и была помечена
как «лучше для ru») разделяет облака:

```
  мусор:  0.42–0.56      верное:  0.58–0.63
```

Теперь порог ИМЕЕТ СМЫСЛ. Он в конфиге: `LOCALVOX_SEARCH_MIN_SIMILARITY` (0.55).
Ниже порога — не «слабое совпадение», а НЕ СОВПАДЕНИЕ: «ничего не нашлось» это
полноценный ответ, и выдать его должен код.

**Живая проверка:** «капрезе» → **0 результатов**. «курица» → 5, похожесть 0.58–0.63.

**Число зависит от модели.** Сменили модель — порог надо ПЕРЕМЕРИТЬ, а не угадать.
Поэтому похожесть каждого результата теперь ВИДНА в выдаче: по ней человек и судит,
и настраивает. Семантический хит без слов запроса и без числа проверить нечем.

### 2. Фрагмент — это отрезок, а не момент

Строка расшифровки — окно в 8–15 секунд, а в интерфейсе стоял один таймкод начала.
Непонятно, что именно сыграет «▶» и когда кончится. Теперь везде — `00:42–00:57 (15 с)`:
и в расшифровке, и в выдаче поиска. Для этого в индексы (лексический и семантический)
добавлен `end_sec`; ревизия индекса `r3` — он пересоберётся сам.

## WP-C55 — Проверка перестаёт быть вахтёром

**Что случилось.** Сессия на 50 минут, 223 строки нормальной расшифровки — а в архиве
ни читаемого текста, ни сводки. Владелец: «Че за херня опять?»

**Цепочка, которую я построил сам:**
1. Модель дала нормальный ответ.
2. Проверка обоснованности нашла в нём «выдумки»: `санкт`, `петербург`, `резюме`,
   `сергей`.
3. Мы попросили модель переписать — а в промпте повтора САМИ предложили ей путь
   отступления: «если содержания нет, верни ровно одну строку: *Содержательной речи в
   записи не распознано*».
4. Модель, которую только что отругали за выдумки, схватилась за эту строку как за
   спасательный круг.
5. Сторож увидел отказ и выбросил ВСЁ.

**А проверка была неправа.** Проверил по расшифровке: **«Сергей» и «муж» в записи ЕСТЬ**
— это ложные срабатывания. А «Санкт-Петербург» — это модель написала так, потому что в
записи сказано **«Питер»**. Синоним, а не выдумка. Владелец: «Питер же есть, и про
Дворцовую площадь, почему выдумки?»

**Почему нельзя лечить словарём синонимов.** Владелец остановил: «не надо опять
собирать эквиваленты, ты достал велосипеды писать». И он прав: список синонимов —
такой же тупик, как список имён. Их бесконечно много, и следующая пара («Питер» /
«Северная столица», «зп» / «зарплата») снова провалится.

**Настоящая причина в другом: проверка не должна решать судьбу документа.**

Она сверяет БУКВАЛЬНО — и в этом её сила (её нельзя уговорить), и её предел (синоним
для неё выдумка). Такая проверка годится в ПРИМЕЧАНИЕ, но не в приговор.

Стало:
* **документ пишется ВСЕГДА** — никакого карантина, никаких «черновиков»;
* сомнения — **пометка**: «стоит перепроверить: … — может быть враньё или неточность»
  (в шапке документа комментарием и в журнале обработки);
* **повторный запрос к модели ВЫБРОШЕН** целиком: он и загонял её в отказ, а заодно
  удваивал время LLM;
* **кнопка «✓ Всё верно»** — антоним «переварить заново». Там человек говорит «машина
  ошиблась, переделай», здесь — «машина придирается, всё нормально». Его слово весомее:
  он читал документ и может послушать запись, машина не может. Вердикт ЗАПОМИНАЕТСЯ
  (`Outcome::Confirmed`): предупреждение, которое возвращается после ответа, перестают
  читать вообще — и тогда настоящее пройдёт мимо.

**Проверено на той самой сессии:** `processed.md` 8.5 КБ, `summary.md` 9.9 КБ, в журнале
— пометка со списком слов. Раньше на этом месте было пусто.

### Интерфейс
* **Плеер записи целиком — сбоку и липкий**: по звуку можно шариться, читая расшифровку,
  не листая страницу туда-сюда. На телефоне уезжает вниз, как раньше.
* **Шапка (поиск + вкладки) липкая** — не долистывать наверх ради каждого перехода.
* **«Перевёрнутый плей, который не нажимается»** — это была кнопка «предыдущие 10 минут»,
  отключённая в начале записи. Кнопка, которая ничего не делает, хуже отсутствующей:
  теперь перемотка по окнам показывается, только если окон больше одного.

## WP-C56 — «Спрашивает он херово»: модель подбрасывала монетку

**Жалоба владельца:** «про торт было в тексте, и само слово есть — пишет, этого нет».

**Разбор по цепочке, а не по догадкам:**
1. Слово «торт» в архиве ЕСТЬ — 6 строк в двух сессиях.
2. Поиск его находит: точный — 5 результатов, гибрид — 5.
3. Чат отвечает «В записях этого нет».
4. Достал ФРАГМЕНТЫ, которые уходят модели, — они правильные, прямо про торт.
5. Скормил тот же промпт модели напрямую — **она ответила верно**.
6. Повторил через API — **снова отказ**. И тут же следующий вызов — верный ответ.

**Ответ был НЕДЕТЕРМИНИРОВАННЫМ.** Температура 0.2 — и модель подбрасывала монетку, а
правило 4 нашего же шаблона («отказ — это ПОЛНОЦЕННЫЙ ответ») делало отказ слишком
привлекательным. Ровно тот же капкан, что мы только что вынули из переспроса LLM: мы
сами предлагаем модели путь отступления и удивляемся, что она им пользуется.

**Три механизма (промпт — просьба, механизм — гарантия):**

1. **Температура 0.** Вопрос к архиву — задача поиска, а не сочинение. Ответ, который
   зависит от броска кубика, — не ответ.
2. **Отказ не принимается на веру, если слова вопроса ЛЕЖАТ во фрагментах.** Мы это
   ЗНАЕМ: лексический поиск нашёл их и вернул `matched`. Значит отказ — ошибка модели, а
   не пустой архив, и мы переспрашиваем с прямым указанием. (Если фрагменты пришли
   только «по смыслу» — отказ правдоподобен, не давим.)
3. **Даже упрямый отказ показывает найденное.** Отказ без источников бесполезен: человек
   не может ни проверить его, ни увидеть, что поиск свою часть сделал. Пусть смотрит
   фрагменты сам — он может, модель не смогла.

**Проверка:** пять одинаковых вопросов подряд — пять одинаковых верных ответов, по 4
источника. До правки тот же вопрос давал то ответ, то отказ.


## WP-C57 — Тревога «RECORDING LOSS», которая врала

**Симптом (владелец):** `RECORDING LOSS: received 119 s of audio over 126 s of real time
(5 % missing)`. «Опять чёт непонятное вылезло».

Подозреваемых было два, и оба оказались настоящими.

**1. Сторож считал звук НЕ ТАМ.** Счётчик стоял на выходе очереди: пока пайплайн разбирал
накопившееся, сторож видел «звука пришло меньше, чем прошло времени» — и кричал о потере,
хотя звук лежал в нашей же очереди. Отставание в своей очереди — это не потеря. Счётчик
переехал к ПРОДЮСЕРУ: считаем то, что забрали у устройства, а не то, что успели разобрать.

**2. А вот вторая причина — настоящий баг, и не в сторожe.** WASAPI loopback **не отдаёт
пакетов, когда в системе тишина**: нечего играть — нечего и захватывать. Дорожка
системного звука от этого не «теряет громкость», она **сжимается во времени**: 126 секунд
мира превращаются в 119 секунд файла, и всё, что записано ПОСЛЕ тишины, уезжает
относительно микрофона. Тревога была громкой, но говорила правду.

**Механизм:** продюсер loopback сверяется со стенными часами и добивает пропущенное
тишиной (порог — четверть секунды, чтобы не реагировать на дрожание планировщика).
Дорожка снова течёт со скоростью времени.

Сторож заодно научился называть дорожку («microphone» / «system audio») — предупреждение,
которое не говорит, ЧТО сломалось, заставляет искать это руками.

## WP-C58 — Тест на удалённой расшифровке: «покрытие», которого не было

Владелец удалил из корня `transcript_uat.txt` — настоящую расшифровку своего разговора,
которой в репозитории не место. На неё опирался тест проверки обоснованности. Файла нет —
тест **молча пропускался**. То есть врал: в списке он зелёный, а не проверяет ничего.

Тест удалён, но его ценность — нет. Он ловил то, чего малый корпус не видит: **на четырёх
словах источника ложные тревоги невидимы**, любое слово ответа находит, на что опереться.
Именно на живом протоколе проверка когда-то объявила выдумками 26 законных слов.

Поэтому в корпус добавлена **длинная запись** — `06-dolgiy-sozvon.toml`: грязь настоящая
(обрывы, «э-э», склеенные слова, искажённые англицизмы, числа словами), разговор
синтетический. Три протокола: длинный честный (обвинений быть не должно), выдуманные числа
и выдуманное имя — они обязаны всплыть даже среди множества законных чисел.

**И длинная запись немедленно поймала ошибку в самой проверке.** Честный протокол был
обвинён в выдумке слова `capacity`.

Причина — ложный инвариант в коде, записанный там как истина: «первая буква не меняется ни
при склонении, ни при транслитерации». Первая половина верна. Вторая — нет:

```
  «капасити» --deunicode--> kapasiti
  английское написание того же звука ---> capacity     (к → k, но англ. пишет c)
  расстояние 3 при бюджете 4 — репаратура проходила бы. Отвергала её ТОЛЬКО первая буква.
```

Первая буква требуется теперь только для слова в РОДНОМ письме записи (там она и правда
переживает любой падеж). Для слова в чужом письме держат бюджет и длина. Это не словарь
эквивалентов — это отмена правила, которое в этом режиме неверно.

Бюджет при этом продолжает держать, и намеренно: «кэш» (`kesh`) отстоит от `cache` на 4
правки из 5 и **остаётся необоснованным**. Растягивать бюджет дальше половины длины —
значит обосновать любой латинский термин чем угодно.

**Корпус: 21 случай, все зелёные.**
